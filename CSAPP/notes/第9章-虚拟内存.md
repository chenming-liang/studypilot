## 1. 三个动机：为什么要虚拟内存

上一章讲缓存时，缓存的对象是**主存里的数据块**；虚拟内存（Virtual Memory, VM）把同样的"缓存"思想再上一层：用 **DRAM 缓存磁盘上的内容**。这一节先回答"为什么需要这样一个抽象"。

**动机 1：高效利用主存（efficient use of main memory）**
- 用 DRAM 作为虚拟地址空间一部分的缓存——只把正在用的部分放进内存。

**动机 2：简化内存管理（simplifies memory management）**
- 每个进程看到**同一个**统一的线性地址空间，不用关心物理内存碎片。

**动机 3：隔离地址空间（isolates address spaces）**
- 一个进程无法干扰另一个进程的内存；用户程序无法访问特权内核信息与代码。

> 直觉：物理内存是一间大宿舍，虚拟内存是给每个进程发一张"自己的房间平面图"——图上位置编号永远整齐划一，实际住哪间由管理员（MMU）安排，谁也看不见别人的房间。

**物理寻址 vs 虚拟寻址**：物理寻址（physical addressing）直接用物理地址（PA）访存，只出现在嵌入式微控制器（汽车、电梯、数码相框）；虚拟寻址（virtual addressing）中 CPU 发出虚拟地址（VA），经 MMU（Memory Management Unit）翻译成 PA 再访存——**所有现代服务器、笔记本、手机**都用它，被称为"计算机科学最伟大的想法之一"。

## 2. 地址空间

**线性地址空间 (linear address space)**：有序的连续非负整数地址集合 $\{0, 1, 2, 3, \dots\}$。

**虚拟地址空间 (virtual address space)**：大小为 $N = 2^n$ 的虚拟地址集合 $\{0, 1, \dots, N-1\}$。
**物理地址空间 (physical address space)**：大小为 $M = 2^m$ 的物理地址集合 $\{0, 1, \dots, M-1\}$。

$n$ 与 $m$ 不必相等；现代系统中通常 $n < m$（见 §10：48 位虚拟地址对 52 位物理地址）。

## 3. VM 作为缓存的工具：页与页表

**概念模型**：虚拟内存是磁盘上的一个 $N$ 字节连续数组；该数组的内容被缓存在物理内存（DRAM 缓存）中。缓存块称为**页 (page)**，大小为 $P = 2^p$ 字节。磁盘上的页叫**虚拟页 (VP)**，DRAM 中的页叫**物理页 (PP)**；虚拟页分三类：**未分配 (unallocated)**、**已缓存 (cached)**、**未缓存 (uncached)**。

### DRAM 缓存与 SRAM 缓存的差异

因为磁盘换页的**miss 惩罚巨大**（DRAM 比 SRAM 慢约 10 倍，磁盘比 DRAM 慢约 10000 倍，一次换页超过 1ms = 百万个时钟周期），DRAM 缓存的组织被惩罚成本主导：

- **大块**：页通常 4 KB（Linux 的 "huge pages" 默认 2 MB、可到 1 GB）；
- **全相联 (fully associative)**：任何 VP 可放任何 PP，无需冲突 miss——因为没硬件实现"多路查找"，用一个大映射函数（页表）替代；
- **复杂的替换算法（软件实现）**：硬件做不了这么复杂，由 OS 负责；
- **写回 (write-back) 而非写通 (write-through)**：写通会把系统拖慢到磁盘速度。

### 页表（Page Table）

**页表**是**页表项 (PTE, Page Table Entry)** 的数组，把虚拟页映射到物理页；它是**每个进程一份**的、存放在 DRAM 中的内核数据结构。每个 PTE 含：
- **valid bit**：该页是否在物理内存中；
- 若 valid=1：**物理页号 (PPN)**；
- 若 valid=0：**磁盘地址**（页在磁盘上的位置），或 null（未分配）。

> 类比缓存：页表就是 DRAM 缓存的"索引结构"——但它是**按虚拟页号索引的数组**，不是 SRAM 缓存那种 tag/set 查表。

### 页命中与缺页

**页命中 (page hit)**：访问的 VM 字在物理内存中——PTE valid=1，直接得到 PPN，翻译完成。

**缺页 (page fault)**：访问的 VM 字不在物理内存中——PTE valid=0，发生一次**异常**（页故障）。处理流程：

1. 用户指令访存，MMU 发现对应 PTE valid=0，触发页故障异常，**提升特权级到内核态**；
2. 调用内核的**缺页处理程序 (page fault handler)**：选择牺牲页（victim，若脏则先写回磁盘），把所需页从磁盘拷入内存，更新 PTE；
3. 处理程序执行 `iret` 指令（类似 `ret`，但还会恢复特权级），**返回并重新执行那条触发故障的指令**——这次页在内存里，成为一次页命中。

> **关键点**：等到真正 miss 才把页拷进 DRAM，这叫**按需调页 (demand paging)**。分配新页时 valid 位保持 0，直到后续 miss 才真正调入。

缺页处理示意（`a[500] = 13` 的例子）：`movl \$0xd, 0x8049d10` 触发异常 → 内核拷页 → `iret` 重新执行该指令。

### 局部性救场：工作集与抖动

VM 看似低效（每次访问都可能换页），但靠**局部性**才成立：

- 程序在任意时刻倾向于访问一组活跃的虚拟页，称为**工作集 (working set)**；时间局部性好的程序工作集更小；
- 若**工作集大小 < 主存大小**：单个进程性能良好（冷 miss 之后）；
- 若**工作集大小 > 主存大小**：发生**抖动 (thrashing)**——页被不停换入换出，性能雪崩；多个进程并发时，若它们的**总工作集 > 主存**也会抖动。

## 4. VM 作为内存管理的工具

每个进程有自己的虚拟地址空间（可看作简单的线性数组），映射函数把地址散布到物理内存各处：

- **简化内存分配**：每个虚拟页可映射到任意物理页，同一虚拟页在不同时刻可存在不同物理页中；
- **共享代码和数据**：把多个进程的虚拟页映射到**同一物理页**（如只读的共享库代码，图中 PP 6）；
- **简化链接与加载**：每个程序有相似的地址空间，代码、数据、堆**总是从相同地址开始**——链接器不需要关心物理布局；`execve` 为 `.text`/`.data` 段分配虚拟页并创建 valid=0 的 PTE，段内容由 VM 系统**按页按需拷贝**。

标准进程地址空间布局（从高到低）：内核虚拟内存（用户不可见）→ 用户栈（`%rsp`）→ 共享库的映射区 → 运行时堆（`brk`，由 malloc 创建）→ 读写段（`.data`/`.bss`）→ 只读段（`.init`/`.text`/`.rodata`，从 `0x400000` 加载）。

## 5. VM 作为保护的工具

给 PTE 扩展**权限位**，MMU 在每次访问时检查：

| 位 | 含义 |
|---|---|
| EXEC | 是否允许执行 |
| SUP | 是否要求内核态（supervisor mode） |
| READ / WRITE | 是否允许读 / 写 |

进程 i 与进程 j 的页表各自独立，权限互不相干。任何违规（如用户态访问 SUP 页、写只读页）都触发保护异常（Linux 里报告为 segmentation fault）。虚拟内存因此提供了一个**方便的检查点（interpositioning point）**来实施保护。

## 6. 地址翻译

**地址翻译 (address translation)** 的形式定义：给定映射 $\text{MAP}: V \to P \cup \{\emptyset\}$，对虚拟地址 $a$：
- $\text{MAP}(a) = a'$：数据在物理地址 $a'$；
- $\text{MAP}(a) = \emptyset$：数据不在物理内存（无效或在磁盘）。

**符号约定**：

| 符号 | 含义 |
|---|---|
| $N = 2^n$ | 虚拟地址空间大小 |
| $M = 2^m$ | 物理地址空间大小 |
| $P = 2^p$ | 页大小（字节） |
| VPN | 虚拟页号（VA 高 $n-p$ 位） |
| VPO | 虚拟页偏移（VA 低 $p$ 位） |
| PPN | 物理页号（PA 高 $m-p$ 位） |
| PPO | 物理页偏移（PA 低 $p$ 位，**等于 VPO**） |

### 单级页表翻译流程

1. 页表基址寄存器 **PTBR**（x86 里是 **CR3**）给出当前进程页表的物理地址——**必须是物理地址**（见下"概念问题"）；
2. 用 VPN 索引页表，取回 PTE：
   - valid=1：得到 PPN，物理地址 = `PPN || PPO`（PPO = VPO）；
   - valid=0：**页故障**，走异常路径；
3. 用 PA 访问缓存/内存取数据。

**页命中五步**（数字为讲义图示顺序）：① CPU 发 VA 给 MMU → ②③ MMU 从内存页表取 PTE → ④ MMU 发 PA 给缓存/内存 → ⑤ 缓存/内存把数据字送回 CPU。
**缺页七步**：① CPU 发 VA → ②③ MMU 取 PTE → ④ valid=0，MMU 触发页故障异常 → ⑤ 处理程序选牺牲页（脏则换出）→ ⑥ 换入新页、更新内存中 PTE → ⑦ 返回原进程、重启出故障指令。

> **概念问题（为什么 PTBR 是物理地址）**：若 MMU 只知道页表的**虚拟**地址，那么为了找到页表，它必须先查页表自己来翻译这个地址——无限自指。所以页表基址必须是物理地址，斩断递归。

**VM 与缓存整合**：翻译（VA→PA）发生在缓存之前——缓存只认识物理地址。PTE 本身也是内存中的普通字，会被缓存；PTE 的命中/未命中与数据缓存命中/未命中是两套独立的账本（PTEA hit/miss 与 PA hit/miss）。

## 7. TLB：加速翻译

页表项像其他内存字一样被缓存在 L1 中，但可能被其他数据引用驱逐，且 PTE 命中也要付出 L1 延迟。**翻译后备缓冲 (Translation Lookaside Buffer, TLB)** 就是专门为此设的小硬件缓存：

- 位于 MMU 内部的**小组相联硬件缓存**；
- 把 **VPN 直接映射到 PPN**，保存少量页的完整页表项；
- MMU 每次翻译**先查 TLB**：TLB 命中就不必访问页表（省掉 k 次查找）。

**TLB 的索引方式**：MMU 用 VA 的 VPN 部分访问 TLB。VPN 被划分为 **TLBI**（TLB 索引，选组）与 **TLBT**（TLB 标签，组内比对）。设 $T = 2^t$ 组，VPN 的低 $t$ 位是 TLBI，其余是 TLBT。

**TLB 命中**：省去一次缓存/内存访问（取 PTE 的那次）。**TLB 未命中**：多付出一次缓存/内存访问去取 PTE；好在 TLB 未命中很罕见——为什么？因为**时间局部性**：程序反复访问少量页，VPN 高度重复。

## 8. 多级页表

**问题**：4 KB（$2^{12}$）页、48 位地址空间、8 字节 PTE 时，单级页表需要
$$2^{48} \cdot 2^{-12} \cdot 2^3 = 2^{39}\ \text{字节} = 512\ \text{GB}$$
比大多数计算机的物理内存还大，不现实。

**解法：多级页表 (multi-level page table)**——只分配页表树中程序实际用到的部分：

- **Level 1 表**：每个 PTE 指向一张下级页表（**常驻内存**）；
- **Level 2 表**：每个 PTE 指向一个页（可像其他数据一样换入换出）。

两级页表的例子（64 位地址、8 KB 页、8 字节 PTE）：2K 已分配虚拟页只占一级表 2 项 + 二级表 2 张；中间 6K 未分配区对应一级表的 null PTE，**不分配二级表**——这正是空间节省的来源。注意图中"64 bit addresses"是讲义标注的配置，实际数字仅为说明层级原理。

**k 级页表翻译**：虚拟地址拆成 `VPN 1 | VPN 2 | … | VPN k | VPO`；从 PTBR 出发，依次用 VPN 1、VPN 2、…、VPN k 索引各级表，最后一级给出 PPN，物理地址 = `PPN || PPO`。

**代价**：k 级页表一次翻译要 **k 次内存加载**（且这些加载**没有空间局部性**——每级表都索引到不同位置）。这正是 TLB 必须存在的理由：TLB 命中把 k 次查找合并为一次。

## 9. 一个完整的简单内存系统

讲义用一个完整的小系统串起 TLB → 页表 → 缓存的全流程（CSAPP 9.6.4 的经典例子）。

**配置**：14 位虚拟地址、12 位物理地址、页大小 64 字节。

- **VPO 为什么 6 位**：页大小 $2^p = 64$，故 $p = 6$；
- **VPN 为什么 8 位**：$n - p = 14 - 6 = 8$；
- **PPO 为什么 6 位**：等于 VPO（页偏移在虚拟/物理地址中位数相同）；
- **PPN 为什么 6 位**：$m - p = 12 - 6 = 6$。

**TLB**：16 项、**4 路组相联** → 4 组（TLBI 2 位）、每组 4 行（TLBT 为 VPN 余下 6 位）。
**页表**：256 项（8 位 VPN 全部覆盖）。
**缓存**：16 行、4 字节块、**直接映射**、物理寻址 → CO 2 位、CI 4 位、CT 6 位。

**例子 1：虚拟地址 0x03D4**（TLB 命中、缓存命中）
- VA = `0x03D4` = 二进制 `0000 0011 1101 0100`：VPN = `00000011`（0x03），VPO = `110100`；
- TLB 查 VPN：组 3、tag 0x03 命中 → PPN = 0x0D；无页故障；
- PA = `PPN || PPO` = `001101 101001` = 0x0D69；
- 缓存查 PA：CO = `01`、CI = `1010`（0xA）、CT = `001101`（0x0D）→ 组 0xA tag 0x0D 命中 → 字节 = 0x36。

**例子 2：虚拟地址 0x0020**（TLB 未命中、缓存未命中）
- VA = `0000 0000 0010 0000`：VPN = 0x00，VPO = 0x20；
- TLB 未命中 → 查页表：VPN 0x00 的 PTE = 有效，PPN = 0x28；
- PA = `0x28 || 0x20` = 0x282；
- 缓存查 PA：CO = `10`、CI = `1000`（0x8）、CT = `001010`（0x0A）→ 未命中 → 从内存取块到组 0x8，字节 = 0x08。

> 讲义中这些表格（TLB 内容、页表、缓存行）是课堂练习素材；笔记只保留结论与查表方法，具体每行内容见讲义 `12-vm-details.pptx` 第 17–23 页。

## 10. Core i7/Linux 案例研究

以 Intel Core i7 与 Linux 为例，看真实系统如何落地前面这些概念：硬件缓存/TLB 层次、48 位地址的四级页表翻译、PTE 字段含义，以及一个让虚拟内存"免费"的 L1 访问技巧。

### 硬件层次

Intel Core i7 的存储层次（讲义 2024 版数据）：每核 4 个核心，各有 32 KB 8 路 L1 d-cache 与 i-cache、64 项 4 路 L1 d-TLB、128 项 4 路 L1 i-TLB、256 KB 8 路 L2 统一缓存与 512 项 4 路 L2 统一 TLB；所有核心共享 8 MB 16 路 L3；DDR3 内存控制器（3 × 64 位，总带宽约 32 GB/s，所有核心共享）；核间 QuickPath 互联（4 条链路，各 25.6 GB/s）。

### 端到端地址翻译

- **48 位虚拟地址**、**52 位物理地址**（备注：为什么物理地址位宽可以超过虚拟地址？为了能同时容纳**多个并发进程**的工作集——每个进程只用自己的 48 位空间，但物理内存要为所有进程的总工作集服务）；
- 4 级页表：VA 拆为 `VPN1 | VPN2 | VPN3 | VPN4 | VPO`，各 9 位（9 位索引对应 $2^9 = 512$ 项，8 字节 PTE 恰好装满一页 4 KB）+ 12 位 VPO；
- 每级页表覆盖的区域递减：L1 每项 512 GB → L2 每项 1 GB → L3 每项 2 MB → L4 每项 4 KB；
- CR3 指向 L1 页表（页全局目录）；逐级查 4 张表得到物理地址。

### PTE 字段

**L1–L3 PTE**（每项指向一张 4K 子页表）：P（子页表是否在内存）、R/W（读写权限）、U/S（用户/内核态权限）、WT（写通/写回策略）、A（reference bit，MMU 读写时置位、软件清零，供 LRU 用）、PS（页大小 4 KB 或 4 MB，仅 L1 定义）、G（全局页，任务切换时不清 TLB）、CD（禁用子页表的缓存）、XD（禁止取指），以及 40 位页表物理基址（强制 4 KB 对齐）。

**L4 PTE**（每项指向一个 4K 页）：多了 **D（dirty bit，写时置位）**，其余字段语义相同（PS 不再定义）。

### 加速 L1 访问的技巧：虚拟索引、物理标签

MMU 在 L1 缓存**之前**执行会让 L1 命中变慢——真实系统用一个观察绕开它：

- **观察**：决定缓存索引 CI 的位在虚拟地址与物理地址中**完全相同**（VPO 与 PPO 相同，且缓存大小设计得让 CI 只落在页偏移内）；
- 于是可以**在地址翻译进行的同时**用 VA 的 CI 位索引缓存（"虚拟索引"），翻译完成后再用 PPN 构成的 CT 做标签比对（"物理标签"）——"**virtually indexed, physically tagged**"；
- 一般 TLB 会命中，PPN 位（CT 位）很快可得；这样 **MMU 被移出关键路径**，虚拟内存对访存性能零影响（比 L1 缓存还快）。

## 11. 内存映射与 mmap

把"页由磁盘支撑"从 swap space 推广到普通文件，就得到内存映射；这一节讲映射文件、fork 的写时复制加速，以及用户态 `mmap` 接口的三个典型用途。

### 从换页到文件

分页意味着程序的每个物理页都由磁盘上的某页支撑——通常那些页属于 **swap space**（交换区）。但若某些页的支撑是**普通文件**呢？这就是**内存映射文件 (memory-mapped files)**：把文件区域映射进进程虚拟内存，读写文件如同读写内存，靠分页机制自动换入换出。

### 写时复制（Copy-on-Write, CoW）

`fork` 创建子进程需要复制父进程整个地址空间——听起来很慢，确实很慢。巧妙做法：

1. 只**复制页表**；
2. 把所有页的 PTE 权限位标记为**只读**；
3. 任一进程真正**写**某页时触发写保护异常，内核才复制该页（并为双方恢复可写权限）。

于是 `fork` 的代价从"复制所有内存"降为"复制页表"；父子共享的只读页（含代码）永不复制。

### mmap 系统调用

```c
void *mmap(void *start, int len, int prot, int flags, int fd, int offset);
```

把文件描述符 `fd` 的文件从 `offset` 起共 `len` 字节映射到进程虚拟内存（优先放在 `start` 地址）。返回映射区起始指针（可能不是 `start`）。

- `start`：可以为 0（由内核挑地址）；
- `prot`：`PROT_READ`（可读）、`PROT_WRITE`（可读或写）、`PROT_EXEC`（可执行）；
- `flags`：
  - `MAP_ANON`：支撑对象是匿名对象，页**按需清零 (demand-zeroed)**；
  - `MAP_PRIVATE`：写时复制对象（对文件的改动不写回文件）；
  - `MAP_SHARED`：共享对象（多进程共享同一内存区，取消映射时经写回机制更新文件）。

**用途**：读大文件（用分页机制把文件带入内存）、共享数据结构（`MAP_SHARED`，有风险）、文件型数据结构（如数据库——load/update/write-back 三件套）、以及**支持 Attack Lab**：在栈不可执行的机器上用 mmap 申请一块 `PROT_EXEC` 的可执行区域，把 `%rsp` 指过去执行攻击代码，完事后恢复原栈并 `munmap`（讲义附完整的内联汇编示例，如 `movq %0,%%rsp` 切换栈指针）。

## 12. Linux 进程的虚拟内存组织

内核如何记录每个进程的虚拟内存：地址空间整体布局、"区域"数据结构，以及缺页异常在 Linux 里的三种处置。

### 地址空间布局

Linux 进程的虚拟地址空间（低到高）：程序文本 `.text`（`0x00400000`）→ 已初始化数据 `.data` → 未初始化数据 `.bss` → 运行时堆（`brk` 以上，malloc 管理）→ 共享库映射区 → 用户栈（`%rsp`）→ **内核虚拟内存**。内核部分**对所有进程相同**（内核代码与数据、每进程独立的结构体如页表/task/mm 结构/内核栈）。

### 用"区域"组织虚拟内存

Linux 把每个进程的虚拟内存组织为一组**区域 (area)**，每个区域一个 `vm_area_struct` 描述：

- `vm_start` / `vm_end`：区域地址范围；
- `vm_prot`：该区域的读写权限；
- `vm_flags`：该区域页是与其他进程**共享**还是**私有**；
- `vm_next`：链表指针（区域链表从 `mm_struct` 的 `mmap` 出发）；
- `mm_struct.pgd`：页全局目录地址，指向 L1 页表（每个进程一个 `task_struct` 等结构）。

### Linux 缺页处理

收到页故障异常后，内核先查出故障地址落在哪个区域，分三种情况：

1. **地址不合法**（不在任何区域，或超出 `vm_end`）→ **segmentation fault**（访问不存在的页）；
2. **权限违规**（如对只读页执行写，PTE 权限与 `vm_prot` 不符）→ **保护异常**（Linux 同样报告为 segmentation fault）；
3. **正常缺页**（合法地址、合法权限，但页不在内存）→ 换入所需页，完成翻译。

> 前两种是 bug（segmentation fault），只有第三种才是虚拟内存机制的日常工作。

---

## 总结

程序员视角：每个进程拥有**私有的线性地址空间**，不会被其他进程破坏。系统视角：VM 通过缓存虚拟内存页来高效利用内存（**只在局部性存在时高效**），简化内存管理与编程，并通过权限检查点简化保护。实现上是**硬件 + 软件**协同：MMU、TLB、异常机制属硬件；缺页处理程序、TLB 管理由软件（内核）完成。
