## 1. 为什么需要链接器

链接不是编程语言的功能，而是把多个已编译模块拼成可运行程序的一道必经工序。这一节回答：为什么要把它交给一个专门的工具来做？

### 编译驱动（Compiler Driver）

```bash
linux> gcc -Og -o prog main.c sum.c
linux> ./prog
```

这条命令背后：`main.c`、`sum.c` 各自经翻译器（cpp 预处理、cc1 编译、as 汇编）**分别编译**为**可重定位目标文件** `main.o`、`sum.o`，再由**链接器 (ld)** 合并为**可执行目标文件** `prog`。链接器就是这道工序的主角。

链接器存在的理由有两条：

**理由 1：模块化**
- 程序可写成**多个较小的源文件**，而非一个庞然大物；
- 可构建**公共函数库**（数学库、标准 C 库）：C 头文件只声明类型，定义放在库中，程序链接时取用。

**理由 2：效率**
- **时间——分别编译 (separate compilation)**：改一个源文件只需重编译它再重链接，无需重编译其他文件；多个文件还可并发编译。
- **空间——库的两种组织方式**：

| | 静态链接 (static linking) | 动态链接 (dynamic linking) |
|---|---|---|
| 可执行文件是否含库代码 | 包含，且**只包含实际用到的**库代码 | **不包含**库代码 |
| 运行时 | 内存映像里只有用到的库代码 | **单份库代码**被所有执行进程**共享** |

> 直觉：静态链接像"复印装订"——把需要的书页直接抄进你的书；动态链接像"借阅"——书里只写"去公共图书馆第几层取"，大家共用一本书。

## 2. 链接器的两步工作

每个 `.o` 都是"独立王国"：里面的地址都**相对自身**（从 0 开始），也不知道别的文件长什么样。链接器要把多个王国拼成一个自洽的可执行文件，总共两步：**符号解析** 和 **重定位**。下面用 `main.c` + `sum.c` 走完全程。

### 贯穿例子：main.c + sum.c

两个文件分别编译成 `main.o`、`sum.o`；每个 `.o` 的地址都相对自身（从 0 开始），链接器要把它们拼成一个自洽的可执行文件。

```c
/* main.c */
int array[2] = {1, 2};
int sum(int *a, int n);          /* 声明，定义在 sum.c */

int main(int argc, char** argv) {
    int val = sum(array, 2);     /* 调用 sum、引用 array */
    return val;
}
```

```c
/* sum.c */
int sum(int *a, int n) {         /* 定义 sum */
    int i, s = 0;
    for (i = 0; i < n; i++) s += a[i];
    return s;
}
```

### 第 1 步：符号解析（引用 ↔ 定义配对）

程序里的**符号 (symbol)** 就是跨文件互相认识的"接头暗号"：函数名与全局变量名。每个 `.o` 的符号表里记录"我定义了谁、我引用了谁"：

| 符号 | 情况 | 类型 |
|---|---|---|
| `main` | 定义于 main.o | 全局符号 |
| `array` | 定义于 main.o（数据 {1,2}） | 全局符号 |
| `sum` | **被引用**于 main.o | 外部符号 |
| `sum` | 定义于 sum.o | 全局符号 |
| `array` | **被引用**于 sum.o | 外部符号 |

链接器把每张清单对一下：main.o 需要的 `sum` 正好 sum.o 有，sum.o 需要的 `array` 正好 main.o 有——**每个引用关联到恰好一个定义**。配对失败（比如把 `sum` 拼写成 `summ`）→ 链接错误 "undefined reference"。

注意 `val`、`i`、`s` 这些**函数内局部变量不在符号表里**——它们在栈上，链接器一无所知。

### 第 2 步：重定位（合并段、搬地址、改引用）

- **合并段**：`main.o` 的 `.text` + `sum.o` 的 `.text` + 系统启动代码 → 一个代码段；`main.o` 的 `.data`（array）+ 系统数据 → 一个数据段。
- **搬地址**：符号从各自 `.o` 的相对位置搬到可执行文件的最终绝对地址——`main` → `0x4004d0`，`sum` → `0x4004e8`，`array` → `0x601018`（反汇编见 §6）。
- **改引用**：原 `.o` 中 `mov`/`callq` 等指令的目标地址是占位符（`00 00 00 00`），按 `.rel.text` 的重定位条目填成真实地址（`R_X86_64_32` 填绝对地址、`R_X86_64_PC32` 填 PC 相对偏移）。

> 直观理解：全校社团合并成大社团——先核对各部门"我们请了谁"是否真有其人（解析），再给所有人分配新工位（搬地址），最后把门口贴的"找 XX"换成新工位号（改引用）。

## 3. 目标文件与 ELF 格式

链接器处理的所有文件都用统一的二进制格式（ELF），但按用途分成三种。这一节讲三种目标文件、ELF 内部结构，以及 `.o` 为什么还不能执行。

### 三种目标文件（模块）

| 类型 | 说明 |
|---|---|
| **可重定位目标文件 (.o)** | 可与其它 `.o` 合并成可执行文件；每个 `.o` 由**恰好一个**源 `.c` 文件产生 |
| **可执行目标文件 (a.out)** | 可**直接复制进内存**并执行的代码与数据 |
| **共享目标文件 (.so)** | 特殊的可重定位文件，可在**加载时或运行时**动态链接进内存（Windows 称 DLL） |

### 为什么 .o 不能直接执行？

.o 是"半成品零件"，差三道工序（正好对应链接器做的事）：

1. **缺最终地址**（重定位没做）：`.o` 里符号从地址 0 排起，指令里的引用全是占位符，CPU 不知道往哪跳；
2. **缺"别人"**（合并没做）：`.o` 只有自己这一个 `.c` 的内容，没有其他 `.o` 的定义、系统启动代码（设置 `argc/argv`、调用 `main`、取返回值）、库函数（如 `printf`）；
3. **缺加载信息**：可执行文件必须有**段头表**（页大小、虚拟地址、内存段），加载器才知道怎么把文件映射进内存；`.o` 只有 section header table。

所以链接 = 把半成品拼成成品。这也是"分别编译"省时间的原理：只重编译改动的 `.c`，再重链接即可。

### ELF 格式

**ELF（Executable and Linkable Format）** 是目标文件的标准二进制格式，统一用于 `.o`、`a.out`、`.so`——统称 **ELF 二进制**。文件内部按 section 组织：

| 段 | 内容 |
|---|---|
| **ELF header** | 字长、字节序、文件类型（.o/exec/.so）、机器类型等 |
| **段头表 (Segment header table)** | 页大小、虚拟地址内存段、段大小（可执行文件必需） |
| **.text** | 代码 |
| **.rodata** | 只读数据：跳转表、字符串常量等 |
| **.data** | **已初始化**的全局变量 |
| **.bss** | **未初始化**的全局变量（"Block Started by Symbol"/"Better Save Space"）；**有段头但不占空间** |
| **.symtab** | 符号表：过程与静态变量名、段名与位置 |
| **.rel.text** | `.text` 的重定位信息（可执行文件中需修改的指令地址与修改指令） |
| **.rel.data** | `.data` 的重定位信息（合并后需修改的指针数据地址） |
| **.debug** | 符号调试信息（`gcc -g`） |
| **段头表 (Section header table)** | 各段的偏移与大小 |

**文件布局 vs 内存布局**：代码和数据**同住一个文件**（ELF），只是分住不同 section。加载进内存时，`.text`/`.rodata`/`.data` 的初始字节直接来自文件；`.bss` 在文件里一个字节都不占（只有"需要 N 字节"的记录），加载时操作系统分配空间并清零；堆和栈是运行时才创建，不在文件里。

**"只读代码段"的澄清**：`.init`、`.text` 是代码（指令），`.rodata` 是**只读数据**（字符串常量、跳转表等）——它和代码并成一个只读段只是因为**加载权限相同**（都只读），不是因为它是指令。

## 4. 符号与符号解析

符号解析是链接器的第一步。要理解它，先弄清符号表里有什么（三类符号）、`static` 如何影响可见性，再看同名符号冲突时链接器按什么规则裁决。

### 三类链接器符号

| 类型 | 定义 | 例子 |
|---|---|---|
| **全局符号 (Global)** | 本模块定义、可被其他模块引用 | 非 static 函数、非 static 全局变量 |
| **外部符号 (External)** | 本模块引用、由**其他模块**定义 | 调用其他文件的函数 |
| **局部符号 (Local)** | 仅本模块定义并引用 | 带 `static` 的 C 函数与全局变量 |

**符号识别示例**（`symbols.c`，讲义 slide16）：

```c
int incr = 1;                       /* 定义全局变量 incr */
static int foo(int a) {             /* 定义局部链接器符号 foo（static） */
    int b = a + incr;
    return b;
}

int main(int argc, char* argv[]) {  /* 定义全局符号 main */
    printf("%d\n", foo(5));         /* printf：外部符号引用 */
    return 0;
}
```

哪些名字会出现在符号表？

| 名字 | 类型 | 进符号表？ | 原因 |
|---|---|---|---|
| `incr` | 全局符号 | 是 | 非 static 全局变量 |
| `foo` | 局部符号 | 是 | `static` 函数——仅本模块定义并引用 |
| `main` | 全局符号 | 是 | 非 static 函数 |
| `printf` | 外部符号 | 是 | 本模块引用、由标准库定义 |
| `"%d\n"` | — | 是（可有名字） | `.rodata` 只读段的全局常量字符串 |
| `a` / `argc` / `argv` | — | 否 | 函数形参，栈上 |
| `b` | — | 否 | 局部变量，栈上 |

可用 `readelf -s symbols.o` 验证。

> **关键区分**：链接器符号里的"局部"指 **static 的全局变量/函数**——它们在 `.data`/`.bss` 有实际存储位置，所以进符号表；函数形参与函数内局部变量在**栈**上，链接器一无所知。

### 局部符号与 static

**例子**（`static-local.c`，讲义 slide17）：

```c
static int x = 15;          /* 文件级 static 全局变量 */
int f() {
    static int x = 17;      /* f 里的局部 static 变量 */
    return x++;
}
int g() {
    static int x = 19;      /* g 里的局部 static 变量 */
    return x += 14;
}
int h() {
    return x += 27;         /* 没有自己的 x，用的是文件级的 x */
}
```

- **局部非 static 变量**：在**栈**上，每次调用重新分配，链接器不关心；
- **局部 static 变量**：在 **.bss 或 .data**（已初始化 → `.data`），本质是"作用域限定在函数内的全局变量"，只初始化一次。

三个 `static int x` 是不同实体，编译器在 `.data` 各分配空间，并在符号表里生成**唯一名字**：

| 声明 | 存储段 | 符号表里的名字 |
|---|---|---|
| `static int x = 15;`（文件级） | `.data` | `x` |
| `f` 里的 `static int x = 17;` | `.data` | `x.1721` |
| `g` 里的 `static int x = 19;` | `.data` | `x.1724` |
| `h` 里的 `x` | — | 引用文件级的 `x`（无自己的定义） |

> 为什么唯一命名：三个 `x` 若在符号表里同名，会违反规则"多个强符号不允许"；加后缀后成为互不干扰的局部链接器符号，只在本模块（.o 文件）内可见。

### 符号的强弱与链接器规则

- **强符号 (strong)**：函数与**已初始化**的全局变量；
- **弱符号 (weak)**：**未初始化**的全局变量（或用 `extern` 声明的）。

**链接器符号规则**：

1. **多个强符号不允许**——每个条目只能定义一次，否则**链接错误**。
2. **强符号 + 多个弱符号 → 选强符号**；对弱符号的引用解析到强符号。
3. **多个弱符号 → 任选一个**（可用 `gcc -fno-common` 覆盖）。

### 链接器谜题：规则的反例与陷阱

五个谜题都是 `p1.c` + `p2.c` 两个文件链接。看谜题的前提：函数和已初始化全局是强，未初始化全局是弱；Rule 1 多强报错、Rule 2 强压弱、Rule 3 多弱任选。

**谜题 1：链接错误（Rule 1）**

```c
/* p1.c */            /* p2.c */
int x;                int x;
p1() {}               p1() {}
```

`int x;` 两个都是弱符号，`x` 本身没问题；**出错的是函数**：两个文件都定义 `p1()`，函数是强符号 → 两个强符号同名 → **链接错误**。

**谜题 2：两个弱符号（Rule 3）**

```c
/* p1.c */            /* p2.c */
int x;                int x;
p1() {}               p2() {}
```

函数名不同（`p1`、`p2`），无冲突；但两个 `int x;` 都是弱符号 → Rule 3 任选其一 → 两个文件里的 `x` 是**同一个变量**。不报错，但 p1、p2 若对 `x` 用途不同会互相干扰——程序员的陷阱。

**谜题 3：写 x 覆盖 y（两个弱，类型不同）**

```c
/* p1.c */            /* p2.c */
int x;                double x;
int y;                p2() {}
p1() {}
```

`int x;`（弱）与 `double x;`（弱）都是弱符号 → Rule 3 任选，`x` 合并到同一个位置；但**链接器不查类型**：p2 把 `x` 当 8 字节 double 写，而 p1 里 `x` 只占 4 字节、紧挨着 `y`：

```
p1.c 数据区：  x (4B) | y (4B)
p2 写 x（8B）：←── 这 8B 写下来 ──→
               x 被写  | y 也被写（覆盖！）
```

→ p1 后来读 `y` 得到垃圾值。

**谜题 4：写 x 覆盖 y（强 + 弱，类型不同）**

```c
/* p1.c */            /* p2.c */
int x=7;              double x;
int y=5;              p2() {}
p1() {}
```

`int x=7;` 已初始化 → 强符号；`double x;` 未初始化 → 弱符号；Rule 2 强压弱 → `x` 解析到 p1 的 `int x=7`。但 p2 仍把它当 8 字节 double 写 → **同样覆盖 `y`**（内存图同谜题 3）。

**谜题 5：共享已初始化变量（强 + 弱）**

```c
/* p1.c */            /* p2.c */
int x=7;              int x;
p1() {}               p2() {}
```

`int x=7;` 强、`int x;` 弱 → Rule 2 选强 → 两个文件里的 `x` 是**同一个已初始化变量**（=7），p2 读写的就是 p1 的那个 `x`。

**类型不匹配完整例子**（`mismatch-var.c` + `mismatch-main.c`，讲义 slide21）：

```c
/* mismatch-var.c */            /* mismatch-main.c */
double x = 3.14; /* 强符号 */     long int x;         /* 弱符号 */
                                int main(int argc, char* argv[]) {
                                    printf("%ld\n", x);  /* 当 long 读 */
                                    return 0;
                                }
```

无警告无错误地编译；链接时 `x` 解析到强符号 `double x = 3.14`，但 main 里按 **long 位模式**读——double 的 8 字节位模式被当 long 解释，打印出垃圾值。

> **关键教训**：链接器只认强/弱，**不看类型**——跨文件共享全局变量时类型不匹配，编译链接全程无提示，运行时才爆炸。

### 弱符号合并的细节（补充知识）

**同名弱符号 = 同一个符号、同一个地址**：多个弱符号同名不构成冲突（不像强符号报错），链接器任选/合并为一个，所有引用都解析到这一个存储位置。对比两条规则：Rule 2（强+弱）最终位置是强符号的；Rule 3（多弱）没有强符号，从弱定义里选一个作为最终位置。

所以谜题 3 里 `int x;`（p1.c）与 `double x;`（p2.c）在符号解析后是**同一个符号、同一个地址**——p1.o、p2.o 各有一条符号表条目 `x`，链接后合并成一条，p1 和 p2 的引用都指向它。

**类型差异在代码层面 = 指令宽度**：编译器按各自声明生成不同宽度的指令，链接器只填地址、不改宽度：

```asm
# p2.c（认为 x 是 double）：写 8 字节
movsd %xmm0, x(%rip)     # movsd = 8 字节操作

# p1.c（认为 x 是 int）：写/读 4 字节
movl $42, x(%rip)        # movl = 4 字节操作
movl y(%rip), %eax
```

p2 写 8 字节落在 4 字节的 `x` 上，多出的 4 字节越界覆盖 `y`（谜题 3/4 的机理）。

**ELF 的 COMMON 符号**：真实机制中，未初始化全局变量（弱符号）是 COMMON 符号（C 的 tentative definition，兼容旧代码）。GNU 链接器合并多个 COMMON 时实际**取最大尺寸**分配——若如此，谜题 3 合并后 `x` 分到 8 字节，p2 写 8 字节恰好不越界，所以讲义用 "**might** overwrite"（可能覆盖）；**必然覆盖的是谜题 4**：`int x=7;`（强，进 `.data` 固定 4 字节）+ `double x;`（弱，被强符号压住，指向那 4 字节），p2 写 8 字节必然越界。

> 一句话：符号解析层面，同名弱符号 = 同一个符号、同一个地址；但"这个地址上放多大对象"各文件各说各话，链接器不协调——覆盖与否取决于最终实际分配的大小。

## 5. 全局变量的工程实践

前几节的强/弱符号规则揭示了不少陷阱（不查类型、写变量覆盖相邻存储）。工程上如何安全地跨文件共享全局变量？本节给出可操作的做法。

### 最佳实践

- **尽量不用**全局变量；必须用则：
  - 能 static 就 **static**；
  - **定义全局变量时初始化**（变成强符号，行为可预期）；
  - **引用外部全局变量用 `extern`**——按弱符号处理，但若某处未定义仍会链接错误。

### .h 文件里的 extern

**例子 1：最简单的 extern 用法**（讲义 slide23）

```c
/* global.h */
extern int g;
int f();
```

```c
/* c1.c */
#include "global.h"

int f() {
    return g + 1;        /* 用 g，但 g 不在这定义 */
}
```

```c
/* c2.c */
#include <stdio.h>
#include "global.h"

int g = 0;               /* 唯一一处定义：已初始化 → 强符号 */

int main(int argc, char* argv[]) {
    int t = f();
    printf("Calling f yields %d\n", t);
    return 0;
}
```

`global.h` 里 `extern int g;` 只是**声明**（弱符号引用），告诉 include 它的文件"g 在别处定义"；`c2.c` 里 `int g = 0;` 才是**定义**（已初始化 → 强符号）——整个程序只有一处定义，符合 Rule 1；`c1.c` 的 `f()` 用的 `g` 解析到 `c2.c` 的定义。讲义 slide23 原文 main 形参为 `char argv[]`（笔误），此处写标准写法 `char* argv[]`。

**例子 2：用宏控制"声明 vs 定义"**（讲义 slide24）

```c
/* global.h */
#ifdef INITIALIZE
    int g = 23;          /* 已初始化 → 定义（强符号） */
    static int init = 1;
#else
    extern int g;        /* 声明（弱引用） */
    static int init = 0;
#endif
```

```c
/* c1.c */
#include "global.h"

int f() {
    return g + 1;
}
```

```c
/* c2.c */
#define INITIALIZE        /* 先定义宏，再 include */
#include <stdio.h>
#include "global.h"

int main(int argc, char* argv[]) {
    if (init)            /* c2.c 里 init == 1 */
        g = 31;
    int t = f();
    printf("Calling f yields %d\n", t);
    return 0;
}
```

同一个 `global.h`，因宏不同展开成两种内容：`c1.c`（未定义 `INITIALIZE`）→ `extern int g;` + `static int init = 0;`；`c2.c`（定义 `INITIALIZE`）→ `int g = 23;` + `static int init = 1;`。于是 `g` 仍只有一处定义（c2.c），`init` 是各自 `.c` 的 static（局部链接器符号，不冲突）。惯用法：**一个头文件同时提供声明和定义**。

**宏控制是怎么工作的**（为什么同一个 `.h` 能展开成两种内容）：这发生在**预处理阶段**，与链接无关。

1. **`#include` 是文本粘贴**：预处理时，`#include "global.h"` 这一行被原样替换成 global.h 的完整内容；
2. **`#define` 是预处理期开关**：`#define INITIALIZE` 只告诉预处理器"这个标记存在"，不占内存、不进符号表，链接器看不到；
3. **每个 `.c` 独立预处理**：c1.c 与 c2.c 各自走自己的预处理流程，互不知道对方定义了啥。

于是预处理后，两个文件实际编译的代码分别是：

```c
/* c1.c（未定义 INITIALIZE）展开后： */
extern int g;            /* 只声明 */
static int init = 0;     /* c1.c 自己的 static */

/* c2.c（先 #define 再 include）展开后： */
int g = 23;              /* 定义（强符号） */
static int init = 1;     /* c2.c 自己的 static */
```

时间线：预处理（粘贴 + 宏展开 + 条件编译）→ 编译（纯 C → 机器码 + 符号表）→ 链接（g 的定义在 c2.o，c1.o 的引用解析过去）。宏 `INITIALIZE` 在第一步结束时就不存在了，编译器与链接器都没见过它。

## 6. 重定位与加载

符号解析之后是重定位：把符号从相对位置搬到最终绝对地址，并修正所有引用。本节看重定位条目的两种填法，以及可执行文件最终如何加载进内存。

### 重定位条目（Relocation Entries）

合并时如何知道每条指令要改哪里、改成什么？靠 `.rel.text` 里的**重定位条目**。`main.o` 的反汇编（`objdump -r -d main.o`）：

```asm
0000000000000000 <main>:
   0: 48 83 ec 08     sub $0x8,%rsp
   4: be 02 00 00 00  mov $0x2,%esi
   9: bf 00 00 00 00  mov $0x0,%edi   # %edi = &array
   a: R_X86_64_32 array               # 重定位条目：绝对地址
   e: e8 00 00 00 00  callq 13 <main+0x13>   # sum()
   f: R_X86_64_PC32 sum-0x4            # 重定位条目：PC 相对
  13: 48 83 c4 08     add $0x8,%rsp
  17: c3              retq
```

- `R_X86_64_32 array`：把 `&array` 的**绝对地址**填进占位；
- `R_X86_64_PC32 sum-0x4`：`callq` 用 **PC 相对寻址**，偏移相对下一条指令。

### 重定位后的 .text

```asm
00000000004004d0 <main>:
  4004d0: 48 83 ec 08   sub $0x8,%rsp
  4004d4: be 02 00 00 00 mov $0x2,%esi
  4004d9: bf 18 10 60 00 mov $0x601018,%edi   # &array → 0x601018
  4004de: e8 05 00 00 00 callq 4004e8 <sum>   # sum() → 0x4004e8
  4004e3: 48 83 c4 08   add $0x8,%rsp
  4004e7: c3            retq
00000000004004e8 <sum>:
  ...
```

`callq` 用 PC 相对寻址调 `sum()`：**0x4004e8 = 0x4004e3（下一条指令）+ 0x5（位移）**。

### objdump 输出怎么读

`objdump -d` 会给每个被反汇编的**可执行段**打印 `Disassembly of section` 标题：

```
prog:     file format elf64-x86-64

Disassembly of section .init:

00000000004003c8 <_init>:
  4003c8:   48 83 ec 08          sub    $0x8,%rsp
  ...

Disassembly of section .text:

00000000004004d0 <main>:
  ...
```

- `.init`、`.text`、`.fini`、`.plt` 等**可执行段**都会出现，函数以 `<函数名>` 标签显示；
- `.rodata`、`.data` 是**数据段**（不可执行），`-d` 不反汇编它们，输出里看不到；
- 看数据段用 `objdump -h`（列所有段头）或 `objdump -s -j .rodata`（hex dump 指定段）。

| 命令 | 作用 |
|---|---|
| `objdump -d prog` | 反汇编可执行段（带段标题、`<函数>` 标签） |
| `objdump -h prog` | 列出所有 section 的偏移/大小 |
| `objdump -s -j .rodata prog` | hex dump 指定数据段内容 |

`-D`（--disassemble-all）连数据段也当指令硬反汇编，会得到乱码，一般不用。

### 加载可执行目标文件

重定位完成后，可执行文件按段加载进内存：

- **系统代码/数据（启动代码）**：链接器合并段时加入的"开机引导"——`_start` 在 `main` 之前运行，负责设置 `argc/argv`、调用 `main`、`main` 返回后把返回值传给 `exit()` 交还系统；其所需数据（如 argv 指针数组）一并放入数据段。这就是 `main` 不是程序第一条指令的原因。
- **只读代码段**（`.init`、`.text`、`.rodata`）与**读/写数据段**（`.data`、`.bss`）**从可执行文件加载**；
- 用户栈（运行时创建，`%rsp`）、共享库的内存映射区、运行时堆（`malloc`，`brk`）在内存中建立；
- 内核虚拟内存对用户代码不可见。
- 典型布局从 0x400000 起，未使用区直到 0。

## 总结

| 概念 | 要点 |
|---|---|
| **链接器作用** | 符号解析 + 重定位；模块化与效率（分别编译、静态/动态库） |
| **目标文件** | `.o`（可重定位）、`a.out`（可执行）、`.so`（共享）；统一 ELF 格式 |
| **ELF 段** | .text / .rodata / .data / .bss / .symtab / .rel.text / .rel.data |
| **符号规则** | 强=函数与已初始化全局，弱=未初始化/extern；多强报错、强压弱、多弱任选；**不查类型** |
| **重定位** | 绝对（R_X86_64_32）与 PC 相对（R_X86_64_PC32）两种地址修正 |
| **加载** | 只读代码段 + 读写数据段映射；栈/堆/共享库运行时建立 |
