## 1. 为什么需要 ECF

处理器只会做一件事：从启动到关闭，每个 CPU 核心逐条读取并执行机器指令。我们已经见过改变控制流的两种机制——**跳转/分支**与**调用/返回**——但它们只能响应**程序自身状态**的变化，无法响应**系统状态**的变化：磁盘数据到达、指令除零、用户按 Ctrl-C、系统定时器到期，程序都无从感知。真实的计算机系统需要一套"异常控制流"（ECF）机制来应对这些外部事件。

这套机制遍布系统各层，是本课程反复出现的主题：

| 机制 | 实现 |
|---|---|
| 异常 (Exceptions) | 硬件 + 内核软件 |
| 进程上下文切换 | 硬件定时器 + 内核软件 |
| 信号 (Signals) | 内核软件 + 应用软件 |
| 非局部跳转 (Nonlocal jumps) | C 运行时库 |

> 历史插曲：60 年代设计"外部事件响应"机制时，人们最担心的事件是**行式打印机着火**——打印太快、润滑不足时纸会烧起来。这一设计一直沿用至今：Linux 内核至今用 "lp0 on fire"（lp0 = line printer 0）作为直连打印机出错的提示消息。CPU 如何"知道"打印机着火，正是本章要回答的问题。

## 2. 异常

异常是最底层的 ECF——完全由硬件与内核软件实现，用户程序通常察觉不到它的存在。这一节讲异常的定义与异常表，以及硬件如何把异常分成"异步中断 / 同步陷阱、故障、中止"四类。

### 异常的定义

**异常 (exception)**：响应某个事件（处理器状态的变化）而**把控制转移到 OS 内核**。内核是常驻内存的那部分操作系统；事件举例：除 0、算术溢出、页故障、I/O 请求完成、键入 Ctrl-C。

异常处理程序（在内核态运行）完成后有三种选择：

- **返回到 I_current**——重新执行当前（出错）指令；
- **返回到 I_next**——执行下一条指令；
- **中止 (abort)**——终止当前程序。

### 异常表（Exception Table）

每类事件有一个**唯一的异常号 k**；k 是**异常表**（又称**中断向量 interrupt vector**）的索引，每次异常 k 发生时调用处理程序 k。异常表本质上就是一张"异常号 → 处理程序地址"的表，硬件按号查表跳转。

### 分类：异步 vs 同步

```
ECF
├─ 异步 (Asynchronous) ──── 中断 (Interrupts)
└─ 同步 (Synchronous) ──── 陷阱 (Traps) / 故障 (Faults) / 中止 (Aborts)
```

**异步异常（中断 Interrupts）**：由**处理器外部**事件引起（通过设置处理器中断引脚指示）。处理程序返回"**下一条**"指令。例子：

- **定时器中断**：外部定时器芯片每隔几 ms 触发一次，内核借此从用户程序**夺回控制权**；
- **I/O 中断**：键盘 Ctrl-C、网络包到达、磁盘数据到达。

**同步异常**：由**正在执行的指令**导致，分三种：

| 类型 | 是否故意 | 是否可恢复 | 返回行为 | 例子 |
|---|---|---|---|---|
| **陷阱 (Trap)** | 故意 | — | 下一条指令 | 系统调用、gdb 断点 |
| **故障 (Fault)** | 非故意 | 可能可恢复 | 重新执行出错指令或中止 | 页故障（可恢复）、保护故障（不可恢复）、浮点异常 |
| **中止 (Abort)** | 非故意 | 不可恢复 | 中止当前程序 | 非法指令、奇偶错误、机器检查 |

> **直观理解**：中断是"外患"（外部设备找上门），陷阱是"请愿"（程序主动请求内核办事），故障是"程序自己闯了祸但还有救"，中止是"闯了祸且没救"。

### 故障的两个例子

**页故障（可恢复）**：

```c
int a[1000];
main() { a[500] = 13; }
```

为什么"在内存里访问数组"会触发页故障？关键事实：**物理内存装不下所有进程的全部内容，一部分页当前在磁盘上**。造成这个状态的有两个机制：**按需分页 (demand paging)**——程序装载时并不把所有内容读进内存，访问到哪一页才调入，没访问过的页从"出生"起就在磁盘上；**换出 (swap out)**——内存紧张时内核把长期未访问的页写回磁盘，腾出物理内存。所以 `a[500]` 所在的页可能从未被调入过，也可能早已被换出——它存在，只是此刻在磁盘上（完整机制详见 [[第9章-虚拟内存|第 9 章-虚拟内存]]）。

执行 `movl` 时的完整流程：

1. CPU 查页表，发现"这页不在物理内存"→ 触发页故障，控制交给内核；
2. 内核查证原因：这个虚拟地址**合法**——页表里有条目，只是页在磁盘上；
3. 内核把页从磁盘拷入内存、更新页表；
4. 返回用户程序，**重新执行那条 `movl`**——这次页在内存里，写入成功。

对用户程序完全透明，只是慢了一点点。

> 类比：办公桌（物理内存）只放常用文件，其余在文件柜（磁盘）。要取一个不在桌上的文件，去文件柜拿一下就好——麻烦，但拿得到。

**无效内存引用（不可恢复）**：

```c
int a[1000];
main() { a[5000] = 13; }
```

`a[1000]` 只映射了约一页地址空间，`a[5000]` 远超数组边界。执行 `movl` 时 CPU 同样"查页表失败"触发页故障，但内核查证后发现：这个虚拟地址**根本没有对应的页表条目**——不是"在磁盘上等搬回"，而是"不存在"。内核没有东西可修，于是向进程发 **SIGSEGV** 信号，进程以 "segmentation fault" 退出。

> **关键辨析**：两个都是页故障，可恢复与不可恢复只差在"原因能否被内核修复"——页在磁盘（有映射）可以搬回重执行；地址非法（无映射）只能终止。判断标准不是故障类型，而是出错的原因本身。

## 3. 系统调用

系统调用是异常的一种（陷阱），也是程序主动请求内核服务的唯一正规通道。这一节讲它的动机与机制（为什么必须经内核、怎么调）、x86-64 调用约定，以及几乎所有系统调用共有的错误处理模式。

### 为什么需要系统调用

程序只要想在**自身进程之外**产生效果（读/写文件、获取当前时间、分配 RAM（`sbrk`）、创建新进程），就必须请内核帮忙。内核有**特殊权限**——能改页表、直接与 I/O 设备通信——所以不能随便跳进它的代码，必须用专门的指令。

以 `fopen` 为例：C 库的 `fopen` 内部调用汇编写的 `open`，而 `open` 几乎不做任何事，真正的工作全部由内核完成：

```asm
# open.S
.global open
open:
    mov $SYS_open, %eax    # 把系统调用号放进 %eax
    syscall                # 特殊指令：陷入内核
    cmp $SYS_error_thresh, %rax
    ja __syscall_error     # 返回值超过阈值 = 出错
    ret
```

反汇编里能看到同一套模式（`mov $0x2,%eax`（open 是 2 号调用）→ `syscall` → `cmp $0xfffffffffffff001,%rax`）：错误阈值即 −4095，返回值超过它视为出错。

### 系统调用约定

- **`%rax` 放系统调用号**；其余参数在 `%rdi, %rsi, %rdx, %r10, %r8, %r9`；**返回值在 `%rax`**，负值表示错误（对应负的 errno）。
- 每个 x86-64 系统调用有唯一 ID 号：

| 号 | 名称 | 描述 |
|---|---|---|
| 0 | read | 读文件 |
| 1 | write | 写文件 |
| 2 | open | 打开文件 |
| 3 | close | 关闭文件 |
| 4 | stat | 获取文件信息 |
| 57 | fork | 创建进程 |
| 59 | execve | 执行程序 |
| 60 | _exit | 终止进程 |
| 62 | kill | 向进程发信号 |

**与普通函数调用的异同**：几乎像函数调用——控制转移、返回后执行下一条指令、用调用约定传参、从 `%rax` 拿结果；但有一个**重要例外**：**由内核执行、特权级不同**。其他差异：函数"地址"（系统调用号）在 `%rax`、用 `errno` 报告错误等。

### 系统调用数量与错误处理

当前 Unix 上有**近 400 个系统调用**（Linux 内核 6.0 列表），许多只在特定场景有用；对比之下 C 库有约 **2 万个**文档化函数。

**几乎所有系统级操作都可能失败**（唯一例外是返回 void 的那几个）。出错时大多返回 **−1** 并设置全局变量 **`errno`** 表示原因。必须**显式检查失败**：

```c
pid_t pid = fork();
if (pid == -1) {
    fprintf(stderr, "fork error: %s\n", strerror(errno));
    exit(1);
}
```

可用**错误报告函数**封装这个重复模式（`fprintf(stderr, ...)` + `exit(1)`）；注意 csapp.c 的错误函数若用 `exit(0)` 需改成 `exit(1)`（退出码 0 表示成功，系统调用失败说明程序没做成它该做的事）。

讲义进一步用 **Stevens 风格错误处理包装 (wrapper)** 简化演示：首字母大写的系统调用（如 `Fork()`）封装了错误处理，"**只有成功才返回**"。这只为便于阅读讲义——**真实程序几乎不该这样用**，因为出错时退出并不总是对的。

## 4. 进程与多任务

上一节讲的是 CPU 如何把控制交给内核；内核拿到控制权后要做的事之一，就是在多个进程之间切换。这一节从"什么是进程"讲起，看进程如何靠虚拟内存与上下文切换获得"独占整台机器"的错觉。

### 什么是进程

**定义**：**进程是一个正在运行程序的实例 (instance of a running program)**——计算机科学中最深刻的思想之一。注意它**不同于"程序"或"处理器"**：程序是"做某事的代码集合"，进程是"装载程序以便运行的容器"——同一程序可以同时有多个进程在跑（比如开两个终端窗口）。

进程给每个程序两个关键抽象——这里的"抽象"是操作系统**故意制造的错觉**：把"内存和 CPU 其实是共享的"这个真相藏起来，让每个进程以为自己在独占使用整台机器，写程序的人就不必操心跟别的进程协调共享资源：

- **私有地址空间 (Private address space)**：每个程序仿佛独占主存——由**虚拟内存**机制提供。实际物理内存被许多进程挤在一起共享，但地址翻译（页表）把各进程的"地址 100"映射到不同的物理格子，彼此看不见、门牌号不撞车；
- **逻辑控制流 (Logical control flow)**：每个程序仿佛独占 CPU——由**上下文切换**机制提供。实际一个核被几十个进程轮流使用（定时器中断每几毫秒触发一次切换），但切换足够快，每个进程都感觉自己在从头跑到尾。

> 类比：私有地址空间像"一栋楼里住着很多房客，每个都以为自己是独栋别墅——房门（页表）隔离得好，看不到邻居"；独占 CPU 像"一台游戏机很多人排队轮流玩，但切换快到每个人都觉得手柄一直在自己手里"。

这个错觉不是免费的：物理内存装不下全部内容时页被换到磁盘，访问到就会触发**页故障**（[[#故障的两个例子|§2]]）；切换进程要保存/恢复寄存器，上下文切换本身有开销——课程后面讲的正是这些代价与破绽。

### 多处理（Multiprocessing）

计算机**同时运行许多进程**：一个或多个用户的应用（浏览器、邮件客户端、编辑器…）+ 后台任务（监控网络与 I/O 设备）。这就是**分时 (time sharing)**：物理内存中各程序占不同区域，但每个进程的代码只看到**为自己方便选择的虚拟地址**（虚拟内存最初就是为了这个发明的）。`top` 命令显示系统常有数百个任务（"tasks"），只有少数处于活动状态。

### 上下文切换（Context Switching）

进程由**内核 (kernel)** 管理——内核是操作系统的核心部分：一块**常驻内存**、有**特殊权限**（能改页表、直接与 I/O 设备通信）的特权软件。普通程序在**用户态**运行、权限受限，要访问硬件或系统资源，唯一的正规通道是 **`syscall` 系统调用**进入内核态（[[#系统调用|§3]]）。

**重要：内核不是独立进程，而是作为某个现有进程的一部分运行**。机器上并不存在一个隐藏的"内核进程"在后台跑；内核只在两类时刻被"借用" CPU——某个进程执行 `syscall` 时、定时器中断或页故障等异常发生时（[[#异常|§2]]）。办完事再把控制交回用户程序。

控制流经**上下文切换 (context switch)** 从一个进程传到另一个——切换动作本身正是在内核里完成的。

**单处理器上**的切换四步：

1. 非执行进程的**寄存器值保存在内存**中（每个进程一份 saved registers）；
2. 切换时**保存当前进程寄存器**到内存；
3. **调度器 (scheduler)** 选出下一个执行的进程；
4. **加载新进程的寄存器**并**切换地址空间**（内核用新页表，PTBR 值随上下文保存）。

**多核处理器**：单芯片多个 CPU，**共享主存（和部分缓存）**，每个核可执行一个独立进程；核到进程的调度由内核完成。注意即便多核，进程数也远多于核数，上下文切换依然频繁发生。

### 并发、顺序与抢占

- 两个进程**并发 (concurrent)**：它们的执行在时间上**有重叠**；否则**顺序 (sequential)**。
- 用户看来并发进程"并行"运行——但它们**可能互相干扰**（并发问题的伏笔）。
- 单处理器现实：同一时刻只有一个进程运行，执行是**交错 (interleaved)** 而非真正并行——仍可能互相干扰。

那么内核怎么"插进"用户程序的执行流？我们的程序里没有"现在运行内核代码"这种指令，但有两个入口：程序主动用**特殊指令 `syscall`**（x86）发起一次"内核调用"，内核可能借机切换到别的程序；或**页故障**等异常（§2）发生。这正好把"异常"和"进程调度"接上了：**异常不只是程序出错，也是操作系统拿回 CPU 的入口**。

## 5. 进程控制（fork/exit/wait/execve）

进程的概念建立后，这一节回答工程问题：如何用系统调用创建进程、终止进程、等待子进程结束、再换一个全新程序来跑？主角是 `fork` / `exit` / `wait` / `execve` 四件套。

### 获取进程 ID

- `pid_t getpid(void)`：当前进程 PID。
- `pid_t getppid(void)`：父进程 PID。

PID 在进程生命周期内不变，但可能被**复用**。每个进程有父进程（进程终止时通知它）；父进程先亡则子进程改由**进程 1（init）** 收养——init 永不终止。（与生物学不同，计算机进程通常活得比孩子久。）

### 进程状态

| 状态 | 含义 |
|---|---|
| **Running（运行）** | 正在执行指令，或只要有核就能执行 |
| **Blocked / Sleeping（阻塞/睡眠）** | 在某个外部事件（通常是 I/O）发生前无法继续执行 |
| **Stopped（停止）** | 被用户动作阻止执行（如 control-Z） |
| **Terminated / Zombie（终止/僵尸）** | 进程结束，但父进程**尚未收到通知** |

### 终止进程

三种原因：收到默认动作为终止的信号（[[#信号|§7]]）、从 `main` 返回、调用 `exit`。

```c
void exit(int status)
```

以状态 `status` 终止；**约定正常返回 0，出错非 0**。`exit` 被调用一次但**永不返回**（少有的不会失败的调用）。

### 创建进程：fork

```c
int fork(void)
```

**父进程**调用 `fork` 创建新运行的**子进程**：

- 向**子进程**返回 **0**，向**父进程**返回**子进程的 PID**；
- 子进程是父进程的**几乎相同拷贝**：获得父进程虚拟地址空间的**相同但独立**的拷贝、父进程**打开文件描述符**的相同拷贝；但 **PID 不同**。

`fork` 有趣（且常令人困惑）之处：**调用一次，返回两次**。概念视图：**完整复制执行状态**（代码、数据、堆、栈、保存的寄存器），指定一个为父、一个为子，分别恢复执行；实际实现用 **写时复制 (copy-on-write)** 避免复制 RAM——只有一方真正写某页时才复制该页。

**fork 示例**（`fork.c`）：

```c
int main(int argc, char** argv) {
    pid_t pid;
    int x = 1;
    pid = Fork();              /* 讲义用 Stevens 包装 Fork()，等价于 fork() + 错误检查 */
    if (pid == 0) {            /* Child：fork 返回 0 */
        printf("child : x=%d\n", ++x);
        return 0;
    }
    /* Parent：fork 返回子进程 PID */
    printf("parent: x=%d\n", --x);
    return 0;
}
```

同一程序多次运行，**两种输出都可能出现**：

```
linux> ./fork
parent: x=0
child : x=2

linux> ./fork
child : x=2
parent: x=0
```

解读：fork 返回时父、子里的 `x` 都是 1，之后各改各的（`++x` → 2、`--x` → 0，地址空间独立）；但 stdout 是共享的打开文件。**父/子执行顺序不可预测**——这正是并发程序的体现（进程图见下节）。

> **精确理解**：fork **不是**"把代码运行多遍"——fork 之前的代码（如 `int x = 1`、`pid = Fork()`）只由父进程执行**一次**；子进程不是从 `main` 开头重新跑，而是**从 fork 返回处接着跑**。fork 之后的代码被两个进程**各执行一遍**（所以 `printf` 一共出现两次）。返回值就是身份牌：子进程拿到 **0**，父进程拿到**子进程 PID（非 0）**，`if (pid == 0)` 据此分流。

### 用进程图建模 fork

**进程图 (process graph)**：捕获并发程序中语句偏序的工具。

- 每个**顶点**是一条语句的执行；`a → b` 表示 a 先于 b 发生；边可标变量当前值；printf 顶点标输出。
- **任何拓扑排序**（所有边从左到右的总顺序）都对应一个**可行全序**。

**`fork2`（连续两次 fork）**：

```c
void fork2() {
    printf("L0\n");
    fork();
    printf("L1\n");
    fork();
    printf("Bye\n");
}
```

4 个进程各打印 `Bye`，`L0` 只出现一次，`L1` 出现两次。可行输出（7 行）：

```
L0
L1
Bye
Bye
L1
Bye
Bye
```

而 `L0 Bye L1 Bye L1 Bye Bye` **不可行**——第一个 `Bye` 出现时还没有任何进程执行过 `L1`，任何进程都到不了 `Bye`（不是拓扑排序）。

![[Pasted image 20260824122342.png]]

**`fork4`（父进程才继续 fork）**：

```c
void fork4() {
    printf("L0\n");
    if (fork() != 0) {          /* 父进程分支 */
        printf("L1\n");
        if (fork() != 0) {      /* 又是父进程 */
            printf("L2\n");
        }
    }
    printf("Bye\n");
}
```

`L0 L1 Bye Bye L2 Bye` **可行**（父进程 L0→L1→L2→Bye，两个子进程各打印 Bye 后父进程的 Bye）；`L0 Bye L1 Bye Bye L2` **不可行**——父进程的 `Bye` 必须在 `L2` 之后，序列里 `L2` 后面没有 `Bye`。

![[Pasted image 20260824122410.png]]

**`fork5`（子进程才继续 fork）**：

```c
void fork5() {
    printf("L0\n");
    if (fork() == 0) {          /* 子进程分支 */
        printf("L1\n");
        if (fork() == 0) {      /* 孙进程 */
            printf("L2\n");
        }
    }
    printf("Bye\n");
}
```

`L0 Bye L1 L2 Bye Bye` **可行**（父进程 L0→Bye，子进程 L1→Bye，孙进程 L2→Bye）；`L0 Bye L1 Bye Bye L2` **不可行**——孙进程的 `Bye` 必须在 `L2` 之后。

![[Pasted image 20260824122433.png]]

### 收割子进程（Reaping）

- **想法**：进程终止后仍占用系统资源（内存、OS 表、退出状态本身）——称为**僵尸 (zombie)**，"活死人"。
- **收割 (reaping)**：父进程对已终止子进程执行（用 `wait`/`waitpid`）；父进程获得退出状态信息；内核随后删除僵尸子进程。
- **父进程不收割会怎样？** 分三种情况：
  - 父进程**活着且是长运行进程**（shell、服务器，永不退出）：不收割则僵尸永远堆积（占内存、耗尽 PID）——**必须显式收割**；
  - 父进程**先终止**：子进程成为孤儿，内核自动把孤儿"过继"给 **init（pid 1）**——init 的职责之一就是收割所有没人管的孩子，僵尸最终被它收走，不用操心；
  - 终止的**正是 init**：孤儿失去最后兜底，只能重启（init 是系统第一个进程，本就不该终止）。
  - 所以**只需在长运行进程（如 shell、服务器）里显式收割**：短命程序就算产生僵尸，等父进程自己也退出后，init 会接管收走。

**僵尸示例**（`fork7`）：

```c
void fork7() {
    if (fork() == 0) {                 /* 子进程 */
        printf("Terminating Child, PID = %d\n", getpid());
        exit(0);                       /* 退出 → 变僵尸 */
    } else {                           /* 父进程 */
        printf("Running Parent, PID = %d\n", getpid());
        while (1);                     /* 无限循环：永不退出、永不收割 */
    }
}
```

`ps` 显示子进程为 `<defunct>`（僵尸）；`kill` 杀掉父进程后再 `ps`，僵尸消失——**init 接管并收割了它**。**非终止子进程**示例：父进程终止后子进程仍活动，必须显式 kill，否则永远运行。

### wait：与子进程同步

**手动收割 = 父进程调用 `wait`/`waitpid`**——这是收割终止子进程的唯一方式：不调用，僵尸就留着。

```c
pid_t wait(int *status)
pid_t waitpid(pid_t pid, int *status, int options)
```

- **`wait`**：挂起当前进程直到**某个**子进程终止；返回该子进程 PID，退出状态存入 `status`。
- **`waitpid`**：更灵活——可等待**特定子进程或一组**；可要求"没有可收割的子进程就立即返回"（`WNOHANG`）。

**`fork9` 示例**（同步收割：父进程 fork 后直接 wait）：

```c
void fork9() {
    int child_status;
    if (fork() == 0) {
        printf("HC: hello from child\n");
        exit(0);
    } else {
        printf("HP: hello from parent\n");
        wait(&child_status);        /* 父进程挂起，等子进程终止并收割 */
        printf("CT: child has terminated\n");
    }
    printf("Bye\n");
}
```

可行输出 `HC HP CT Bye` 或 `HP HC CT Bye`（`CT` 必须在子进程终止即 `HC` 之后）；`HP CT Bye HC` **不可行**——`CT` 不可能出现在 `HC` 之前。

![[Pasted image 20260824123337.png]]

**状态码**：`wait` 的返回值为终止子进程的 PID；`status` 需用 `sys/wait.h` 宏解码——`WIFEXITED` / `WEXITSTATUS`（正常退出与退出码）、`WIFSIGNALED` / `WTERMSIG`（被信号终止与信号号）、`WIFSTOPPED` / `WSTOPSIG`、`WIFCONTINUED`。多个子进程完成时，`wait` **按任意顺序**收取（`fork10`）；`waitpid(pid[i], ...)` 可按指定顺序（`fork11` 从 N−1 到 0 收割，必定逆序）。

**两种收割时机**：

- **同步收割**：父进程主动 `wait` 挂起等待，直到子进程终止（如 fork9）；
- **异步收割**：装 `SIGCHLD` 处理程序，handler 里循环 `wait` 收割（见 [[#不能用信号计数事件|§8 的 child_handler2]]）——shell 必须用异步式，因为它不能阻塞在 `wait` 上等某个孩子，还要读下一条命令；
- **命令行注意**：不能 kill 僵尸本身（它已死，SIGKILL 无效）；父进程不收割时，只能杀掉父进程让 init 接管收割。

### execve：加载并运行程序

**execve 不创建进程，而是把当前进程整个换掉**——"换芯不换壳"：进程这个容器（PID、打开的文件、信号上下文）原样保留，里面装的程序整个换成新的（fork 是克隆出另一个你，execve 是把自己整容成另一个人——身份证号不变，人换了）。

```c
int execve(char *filename, char *argv[], char *envp[])
```

- **在当前进程中**加载并运行可执行文件 `filename`（目标文件或 `#!interpreter` 开头的脚本），带参数列表 `argv`（约定 `argv[0]==filename`）与环境变量列表 `envp`（`"name=value"` 字符串，如 `USER=droh`；`getenv`/`putenv`/`printenv`）。
- **覆盖代码、数据与栈**；**保留 PID、打开的文件与信号上下文**。

**调用一次，永不返回**——除非出错。原因：execve 成功后旧程序的代码已被覆盖，调用点与返回地址都不复存在，根本没有"返回"可言；新程序从自己的 `main` 开始跑，execve 后面的代码永远执行不到。唯一例外是失败（文件不存在、没权限等）：此时旧程序还活着，返回 −1，可处理错误（shell 打印 "Command not found" 后 `exit(127)`）。

**与 fork 的组合拳**：execve 会换掉当前进程，直接调用等于"自杀式换装"——所以它几乎总是和 fork 一起用：

```c
if ((pid = fork()) == 0) {           /* ① 子进程：复制一份自己 */
    execve(argv[0], argv, environ);  /* ② 子进程换成用户要跑的程序 */
    exit(127);                       /* 只有 execve 失败才到这 */
}
/* ③ 父进程（shell 本体）毫发无损，继续读下一条命令 */
```

这就是 shell 的运行原理（[[#Shell 程序|§6]]）：**fork 造容器，execve 装程序**——"进程是程序的容器"在这里落地。

新程序启动时栈的布局（自顶向下）：环境变量字符串（`envp[n] == NULL` 结尾）、命令行参数字符串（`argv[argc] == NULL` 结尾）、`envp`/`argv`/`argc` 分别由 `%rdx`/`%rsi`/`%rdi` 指向。

与内存布局的关系：`execve` 释放旧区域的 `vm_area_struct` 与页表，为新区建新的——程序文本与已初始化数据由目标文件（file-backed）支撑，`.bss` 与栈由匿名文件（demand-zero）支撑，PC 设为 `.text` 入口点（细节详见 [[第9章-虚拟内存|第 9 章-虚拟内存]]）。

## 6. Shell 程序

把进程控制的系统调用组合起来，就能写一个真正有用的程序——Shell。这一节拆解一个极简 Shell 的实现，并指出它遗留的问题（后台任务变僵尸），为信号出场做铺垫。

### 什么是 Shell

**Shell 是一个应用程序**，代用户运行程序。`sh`（Bourne，1977）、`csh`/`tcsh`、`bash`（默认 Linux shell）。桌面界面（Windows/Mac）本质也是 shell——其主要职责是替你启动程序，甚至内部可能就叫 shell。

### 简单 Shell 示例

```
linux> ./shellex
> /bin/ls -l csapp.c
-rw-r--r-- 1 bryant users 23053 Jun 15 2015 csapp.c
> /bin/sleep 10 &
32031 /bin/sleep 10 &
> /bin/ps
...
> quit
```

必须给出**完整路径名**（shellex 没有 PATH 查找）；`&` 结尾在**后台**运行——shell 打印子进程 PID 后立即返回提示符，`sleep` 继续在后台跑。

### 基本循环与 eval 函数

Shell 的执行是 read/evaluate 的序列：读命令行 → 执行请求的操作（**内建命令**，本示例只实现 `quit`；或**从文件加载并执行程序**）。核心是 `eval`：

```c
void eval(char *cmdline) {
    char *argv[MAXARGS];
    char buf[MAXLINE];
    int bg;
    pid_t pid;

    strcpy(buf, cmdline);
    bg = parseline(buf, argv);              /* 解析命令行，返回是否以 & 结尾 */
    if (argv[0] == NULL) return;            /* 忽略空行 */
    if (!builtin_command(argv)) {           /* 不是内建命令 */
        if ((pid = fork()) == 0) {          /* 子进程运行用户任务 */
            execve(argv[0], argv, environ);
            /* 能走到这里说明 execve 失败 */
            printf("%s: %s\n", argv[0], strerror(errno));
            exit(127);                      /* 127 = "execve failed" */
        }
        if (!bg) {                          /* 前台：等待子进程结束 */
            int status;
            if (waitpid(pid, &status, 0) < 0)
                unix_error("waitfg: waitpid error");
        }
        else                                /* 后台：打印 pid 继续 */
            printf("%d %s\n", pid, cmdline);
    }
    return;
}
```

`parseline` 把 `buf` 解析进 `argv` 并返回是否以 `&` 结尾；`execve` 只在出错时返回（约定退出码 127 表示 "execve failed"）。

### 简单 Shell 的问题

Shell **设计为无限运行**，不应累积无用资源（内存、子进程、文件描述符）。示例 shell 正确等待并收割**前台**任务；但**后台任务**终止后变成僵尸，**永远不会被收割**（因为 shell 通常不终止）——最终可能耗尽整台计算机的内存，更可能**耗尽 PID**。

> 关键矛盾：shell 需要收割后台进程，又不能为它们阻塞在 `wait` 里（还要读下一条命令）。它怎么知道何时去收割？这正是下一节**信号**要解决的问题——进程如何响应"不止一种外部事件、哪个先来算哪个"。

## 7. 信号

上一节遗留的问题——shell 怎么知道后台子进程何时终止——正是信号要解决的。信号是内核发给进程的小消息，这一节讲信号的概念、发送与接收、待决与阻塞、默认动作与安装处理程序，以及编写安全处理程序的 G0–G5 指南。

### 信号的概念

**信号 (signal)**：通知进程系统发生某类事件的小消息，类似异常与中断；由内核（有时应另一进程请求）发给进程；用**小整数 ID（1–30）** 标识；信号携带的唯一信息就是 ID 与"它到了"。

| ID | 名称 | 默认动作 | 对应事件 |
|---|---|---|---|
| 2 | SIGINT | 终止 | 用户键入 ctrl-c |
| 9 | SIGKILL | 终止 | 杀死程序（**不能覆盖或忽略**） |
| 11 | SIGSEGV | 终止 | 段违规 |
| 14 | SIGALRM | 终止 | 定时器信号 |
| 17 | SIGCHLD | **忽略** | 子进程停止或终止 |

### 发送信号与进程组

内核通过**更新目标进程上下文中的状态**发送信号（讲义特意回避教科书里"delivered"这个歧义词）。原因两种：

- 内核检测到系统事件（如除 0 → SIGFPE、子进程终止 → SIGCHLD）；
- 另一进程调用 **`kill` 系统调用**显式请求。

**进程组 (Process Groups)**：每个进程属于**恰好一个进程组**；`getpgrp()` 返回当前进程组、`setpgid()` 改变进程组。shell 为前台作业和每个后台作业各建一个进程组（组号取组长 PID）。发送信号的三种途径：

- **键盘**：ctrl-c / ctrl-z 使内核向**前台进程组**每个任务发 **SIGINT**（默认终止）或 **SIGTSTP**（默认停止）——注意是发给整个前台进程组，不是单个进程；
- **`/bin/kill` 程序**：`/bin/kill -9 24818` 发 SIGKILL 给进程；`/bin/kill -9 -24817` 发 SIGKILL 给**整个进程组**（负号表示组）；
- **`kill` 函数**：`kill(pid[i], SIGINT)` 向指定进程发信号。

### 接收信号与待决/阻塞

目标进程收到信号 = 被内核**强制**以某种方式反应：**忽略**、**终止**（可选 core dump）、**捕获**（执行用户级**信号处理程序**，类似响应异步中断的硬件异常处理程序）。

先分清四个概念——**发送 ≠ 接收**：

| 概念 | 含义 | 谁做 |
|---|---|---|
| **发送 (sending)** | 内核把信号"记"到目标进程头上（置位） | 内核 |
| **待决 (pending)** | 信号已发送、进程还没处理 | 状态 |
| **接收 (receiving)** | 内核强制进程对信号做出反应（忽略/终止/捕获） | 内核 |
| **阻塞 (blocked)** | 进程声明"这类信号我不要"（可发送但暂不处理） | 进程（`sigprocmask`） |

发送只是"记账"，进程毫无感觉；真正"被处理"发生在接收时。要点展开：

- **每种信号最多一个待决——信号不排队**：已有类型 k 的待决信号时，后续同型信号被**丢弃**。原因：pending 是一位（只有 0/1、没有"几条"），同型信号来 10 次位也只从 0→1 一次，其余丢弃——它只告诉你"这类事件**发生过**"，不告诉"发生了几次"（这正是 [[#不能用信号计数事件|§8]]"不能用信号计数事件"的根源）。
- **阻塞 ≠ 丢弃**：阻塞期间到达的信号 pending 位照样置 1，只是内核暂不处理；解除阻塞后若仍在 pending，会立即被处理——阻塞只是推迟。
- `SIGKILL`、`SIGSTOP` 不能被阻塞；`SIGSEGV`、`SIGILL` 等由 CPU 异常触发的信号**只能阻塞来自其他进程的发送**（如 `kill -11 pid`），CPU 异常触发时内核不理会阻塞。
- 一个待决信号**至多被接收一次**：pending 位从 1 变 0 只发生在接收那一刻，一次待决期间不会被处理两遍。
- 内核在每个进程上下文中维护 **pending 与 blocked 位向量**：发送类型 k 信号 → 置 pending 第 k 位；接收 → 清除；blocked（又称**信号掩码 signal mask**）可用 `sigprocmask` 设置/清除。

> 类比：pending = 微信的"未读消息"，blocked = 给某人设了免打扰——消息照样发进来（未读 +1），但你不收到提醒，解除免打扰后一起处理；pending 一位 = 只有"亮/灭"两档的灯泡，连按 10 次还是亮的，不记录次数。

### 接收算法的内核侧

**接收发生在什么时刻**：信号不是发来就立刻处理——内核把信号先记在 pending 账本上，在**从异常处理程序返回、准备把控制权交还给进程 p 时**批量结算（讲义 slide42 的场景）。

设 `pnb = pending & ~blocked`（进程 p 的**待决且非阻塞**信号集）：

- 若 `pnb == 0`：无事发生，控制传给 p 逻辑流的下一条指令；
- 否则：选 pnb 中**最低非零位 k**，强制 p 接收信号 k（触发默认动作或 handler），并清掉该位；对 pnb 中所有非零 k 重复；再把控制传给下一条指令。

> 直觉：内核像"攒着账单、每次结一次"的管家——信号来了先记在 pending 账本上，等要把控制权还给进程时，把该处理的信号一次性处理掉（编号小的先处理）。

### 默认动作与安装处理程序

每类信号有预定义**默认动作**：进程终止；进程停止直到 `SIGCONT`；进程忽略。

> 对比：信号有"默认动作"，CPU 异常则不然——若操作系统没有为某种 CPU 异常提供处理程序，CPU 调用缺失处理程序时**整台计算机会崩溃**。所以异常处理程序必须齐全，信号则可以有默认行为兜底。

**handler（信号处理程序）**：本质就是一个普通的 C 函数，专门处理某类事件；与普通函数的区别是**不是由你调用，而是由内核在信号到达时替你调用**。三步：

1. **安装 (install)**：`signal(SIGINT, sigint_handler)` 把 handler 的地址注册给某信号——只是登记，此时什么都没做；
2. **触发（捕获, catch）**：进程收到该信号时，内核强制中断当前代码，跳到 handler 执行；
3. **返回**：handler 执行完 `return`，控制回到被中断的指令。

安装处理程序：

```c
handler_t *signal(int signum, handler_t *handler);
```

- `SIG_IGN`：忽略该类信号；`SIG_DFL`：恢复默认动作；否则 `handler` 是用户级处理程序地址（"安装"；执行它叫"捕获/处理"）。返回时控制回到被中断的指令。
- 警告：本讲义用 `signal` 简化，实际应使用 `sigaction`。

> 类比：handler 像留给前台的纸条"快递到了打这个电话"——电话号码就是 handler 地址；安装 = 把纸条交给前台，捕获 = 快递到了前台替你拨号；不装 handler = 没留纸条，快递按默认方式处理。

**示例**（`sigint.c`）：装好后按 Ctrl-C，程序**不终止**（默认动作被覆盖），而是打印那段话再退出——这就是"捕获"的效果。讲义 slide46 原用 `printf` 仅为演示，实战按 G1 应换 SIO 安全版：

```c
void sigint_handler(int sig) {          /* SIGINT 处理程序 */
    sio_puts("So you think you can stop the bomb with ctrl-c, do you?\n");
    sleep(2);
    sio_puts("OK. :-)\n");
    _exit(0);                            /* 用 _exit 而非 exit */
}
int main() {
    signal(SIGINT, sigint_handler);   /* 安装 */
    pause();                          /* 等待信号 */
    return 0;
}
```

### 处理程序是并发流

信号处理程序是与主程序**并发的独立逻辑流**（不是进程），仅存在到返回主程序为止；处理程序可被其他处理程序**中断（嵌套）**——主程序 → handler S → handler T → 返回 S → 返回主程序。

### 阻塞与解除阻塞

**为什么需要阻塞**：handler 是并发流，随时可能插进来打断主程序——正在修改共享数据结构时被打断就坏了。阻塞让进程声明"这段代码跑完之前，别让这类信号进来"。

- **隐式**：内核自动阻塞**当前正在处理的类型**的待决信号——SIGINT 的 handler 执行期间，再来的 SIGINT 不会立刻再次进入 handler（要等这次返回）。注意只挡**同类型**：handler S 执行时来了**不同类型**的 t，照样打断 S、嵌套进入 handler T。
- **显式**：`sigprocmask` 自己控制；配套 `sigemptyset`（建空集）、`sigfillset`（全加入）、`sigaddset`（加入）、`sigdelset`（删除）。

```c
sigset_t mask, prev_mask;
sigemptyset(&mask);
sigaddset(&mask, SIGINT);
sigprocmask(SIG_BLOCK, &mask, &prev_mask);   /* ① 阻塞 SIGINT，旧掩码存进 prev_mask */
/* ... 不会被 SIGINT 中断的临界区 ... */       /* ② 放心改共享数据 */
sigprocmask(SIG_SETMASK, &prev_mask, NULL);   /* ③ 恢复旧掩码，解除 SIGINT 阻塞 */
```

三步走：① 组装集合（要阻塞谁）；② `SIG_BLOCK` 追加阻塞并**保存旧掩码**——调用前可能已有别的信号被阻塞（如 SIGCHLD），恢复时不能把它们也清掉；③ `SIG_SETMASK + prev_mask` 把阻塞集整个恢复原状——临界区前后状态一致。另有 `SIG_UNBLOCK`（把集合里的信号移出阻塞集）。

- **典型应用**：G3 保护共享数据（handler 里改 job 表前 `sigfillset` 阻塞所有信号，改完恢复）；[[#同步流以避免竞态（Race）|§8 竞态修复 procmask2]]（fork 前阻塞 SIGCHLD、`addjob` 后恢复）。

### 编写安全处理程序的指南（G0–G5）

处理程序与主程序并发、共享同一份全局数据结构，容易破坏共享数据。指南：

- **G0**：处理程序**尽量简单**（如置全局标志后返回）。
- **G1**：只调用**异步信号安全 (async-signal-safe)** 的函数——`printf`、`sprintf`、`malloc`、`exit` **不安全**！
- **G2**：进入/退出时**保存并恢复 errno**（防止其他处理程序覆盖）。
- **G3**：访问共享数据结构时**临时阻塞所有信号**防损坏。
- **G4**：全局变量声明为 **`volatile`**（防止编译器放进寄存器）。
- **G5**：全局标志声明为 **`volatile sig_atomic_t`**（只读或只写，如 `flag = 1` 而非 `flag++`），此类标志无需像其他全局那样保护。

### 异步信号安全性（Async-Signal-Safety）

函数**可重入 (reentrant)**（所有变量在栈帧上）或**不被信号中断**则安全。POSIX 保证 **117 个**函数安全（`man 7 signal-safety`）。常见的：`_exit`、`write`、`wait`、`waitpid`、`sleep`、`kill`。常见但**不在列表**：`printf`、`sprintf`、`malloc`、`exit`。

> **不幸的事实：`write` 是唯一异步信号安全的输出函数。** 要在处理程序里格式化输出，用 csapp.c 的 **SIO（安全 I/O 库）**——`sio_puts`、`sio_putl`、`sio_error`、`sio_printf`（识别 `%c %s %d %u %x %%`）——上面 [[#默认动作与安装处理程序|§信号示例]] 的安全版用的正是它。

## 8. 正确的信号处理

信号机制本身藏着几处容易写错的陷阱：待决信号不排队、处理程序与主程序的竞态、等待信号的方式。这一节给出三个经典场景的错误写法与正确写法。

### 不能用信号计数事件

**反例 `fork14`（错误！）**：

```c
/* fork14（错误版）：用信号计数子进程终止次数 */
volatile int ccount = 0;                 /* G4：handler 在编译器看不见的地方改它 */
void child_handler(int sig) {            /* SIGCHLD handler */
    int olderrno = errno;
    pid_t pid;
    if ((pid = wait(NULL)) < 0)          /* 每次调用只收割一个！ */
        Sio_error("wait error");
    ccount--;
    errno = olderrno;
}
void fork14() {
    pid_t pid[N];
    int i;
    ccount = N;
    signal(SIGCHLD, child_handler);
    for (i = 0; i < N; i++)
        if ((pid[i] = fork()) == 0) {    /* 子进程 */
            sleep(1);                    /* N 个子进程几乎同时终止 → SIGCHLD 合并 */
            exit(0);
        }
    while (ccount > 0)                   /* 父进程自旋等 ccount 归零 */
        ;
}
```

N 个子进程 `sleep(1); exit(0)`（几乎同时终止），父进程安装 `SIGCHLD` handler 后 `while (ccount > 0);` 自旋，handler 每次调用只 `wait` 一个就 `ccount--`。但**待决信号不排队**（每种信号一位 pending 位，同类至多一个）——多个子进程同时终止时 `SIGCHLD` 被**合并**，handler 每次调用只 reap 一个 → `ccount` 永远到不了 0，**挂起**。

> 教训：**不能靠信号计数事件**（如子进程终止次数）。信号能告诉你的只是"某类事件**发生过**"，不是"发生了几次"。

**正确写法 `child_handler2`**：**把 `wait` 放进循环**，一次调用收割所有已终止子进程：

```c
void child_handler2(int sig) {
    int olderrno = errno;
    pid_t pid;
    while ((pid = wait(NULL)) > 0) {   /* 收割所有已终止子进程 */
        ccount--;
        ...
    }
    if (errno != ECHILD) sio_error("wait error");
    errno = olderrno;
}
```

### 同步流以避免竞态（Race）

**反例（`procmask1.c`）**：

```c
/* procmask1.c：错误版——fork 之前没有阻塞 SIGCHLD */
void handler(int sig) {                        /* SIGCHLD 处理程序 */
    int olderrno = errno;
    sigset_t mask_all, prev_all;
    pid_t pid;
    sigfillset(&mask_all);
    while ((pid = waitpid(-1, NULL, 0)) > 0) { /* 收割所有已终止子进程 */
        sigprocmask(SIG_BLOCK, &mask_all, &prev_all);
        deletejob(pid);                        /* 从作业表删除该子进程 */
        sigprocmask(SIG_SETMASK, &prev_all, NULL);
    }
    if (pid != 0 && errno != ECHILD)
        sio_error("waitpid error");
    errno = olderrno;
}

int main(int argc, char **argv) {
    int pid;
    sigset_t mask_all, prev_all;
    int n = N;                                 /* N = 5 */
    sigfillset(&mask_all);
    signal(SIGCHLD, handler);
    initjobs();                                /* 初始化作业表 */
    while (n--) {
        if ((pid = fork()) == 0)               /* 子进程 */
            execve("/bin/date", argv, NULL);   /* date 很快跑完、立即终止 */
        sigprocmask(SIG_BLOCK, &mask_all, &prev_all);  /* 父进程：addjob 前才阻塞（太晚！） */
        addjob(pid);                           /* 加入作业表 */
        sigprocmask(SIG_SETMASK, &prev_all, NULL);
    }
    exit(0);
}
```

子进程 `execve("/bin/date")` 可能**在父进程 fork 返回后、执行到 `sigprocmask` 之前**就跑完并终止 → SIGCHLD 到达时 `addjob` 还没执行 → handler 里 `deletejob(pid)` 删了一条**还没加的记录** → 竞态。

**修正（`procmask2.c`）**：在 fork **之前**阻塞 SIGCHLD，父进程 `addjob` 之后解除阻塞；子进程 `execve` 前解除阻塞：

```c
sigprocmask(SIG_BLOCK, &mask_one, &prev_one);   /* 父：阻塞 SIGCHLD */
if ((pid = fork()) == 0) {
    sigprocmask(SIG_SETMASK, &prev_one, NULL);  /* 子：execve 前解除 */
    execve("/bin/date", argv, NULL);
}
sigprocmask(SIG_BLOCK, &mask_all, NULL);        /* 父：addjob 期间阻塞所有 */
addjob(pid);                                    /* 加入作业表 */
sigprocmask(SIG_SETMASK, &prev_one, NULL);      /* 父：解除阻塞 */
```

> 直觉：把 `fork` 与 `addjob` 之间的"窗口期"保护起来——阻塞 SIGCHLD 保证 handler 的 `deletejob` 不可能插进 `fork` 和 `addjob` 之间。这是"阻塞信号 + 临界区"模式的典型应用。

### 显式等待信号

**示例**（`waitforsignal.c`，讲义 slide62–63）：主程序显式等待 SIGCHLD——handler 里 `pid = waitpid(-1, NULL, 0)` 收割并存入全局 `pid`，主程序轮询等它非零。

```c
/* waitforsignal.c：主程序显式等待 SIGCHLD（自旋版） */
volatile sig_atomic_t pid;                 /* G5：handler 写、主程序读 */

void sigchld_handler(int s) {
    int olderrno = errno;
    pid = waitpid(-1, NULL, 0);            /* 收割并把 PID 存入全局 pid */
    errno = olderrno;
}

int main(int argc, char **argv) {
    sigset_t mask, prev;
    int n = N;                             /* N = 10 */
    signal(SIGCHLD, sigchld_handler);
    sigemptyset(&mask);
    sigaddset(&mask, SIGCHLD);
    while (n--) {
        sigprocmask(SIG_BLOCK, &mask, &prev);   /* 阻塞 SIGCHLD */
        if (fork() == 0)                        /* 子进程 */
            exit(0);
        pid = 0;                                /* 重置，等下一次 */
        sigprocmask(SIG_SETMASK, &prev, NULL);  /* 解除阻塞 */
        while (!pid)                            /* 自旋等 handler 填 pid */
            ;
        printf(".");                            /* 收到 SIGCHLD 后做点事 */
    }
    printf("\n");
    exit(0);
}
```

等待那一段的三种写法对比：

- `while (!pid);` —— **自旋**：正确但**浪费**（busy-wait）；
- `while (!pid) pause();` —— **存在竞态**：检查 `pid` 与进入 `pause` 之间可能已收到信号（信号在 `pause` 前到达 → 永久挂起）；
- `while (!pid) sleep(1);` —— 安全但**慢**（最多 1 秒才响应）。

**解决：`sigsuspend`**——"设置掩码 + pause + 恢复掩码"的**原子（不可中断）**版本：

```c
int sigsuspend(const sigset_t *mask);
/* 等价于原子的：
   sigprocmask(SIG_SETMASK, &mask, &prev);
   pause();
   sigprocmask(SIG_SETMASK, &prev, NULL);  */

pid = 0;
while (!pid)
    sigsuspend(&prev);     /* 原子地解除 SIGCHLD 阻塞并等待 */
```

把自旋版的 `while (!pid);` 换成 `while (!pid) sigsuspend(&prev);`，main 其余部分不变，即得最终版（讲义 slide66）——`sigsuspend(&prev)` 原子地完成"把阻塞集临时设为 `prev`（不含 SIGCHLD）+ pause + 恢复"，检查与等待之间不会被信号插入。

## 9. 非局部跳转

最后一类 ECF 不涉及内核：C 运行时库提供的 `setjmp`/`longjmp`。它允许程序受控地打破调用/返回纪律，常用于错误恢复与信号处理。

**它解决什么问题**：错误可能发生在深层嵌套函数里，普通写法要一层层返回错误码、层层检查——又臭又长。setjmp/longjmp 的思路：出错时直接"传送"回顶层预先标记的位置，跳过中间所有层。

> 类比：setjmp = 在某处放一个**传送门标记**；longjmp = 不管在多深的房间里直接瞬移回标记处——中间的房间（栈帧）全都不经过了（普通 return 是走楼梯一层层下，longjmp 是从 10 楼直接跳回 1 楼大厅）。

### 机制

**非局部跳转 (nonlocal jump)**：强大（但危险）的用户级机制，把控制转移到任意位置——**受控地打破过程调用/返回纪律**，用于错误恢复与信号处理。

```c
int setjmp(jmp_buf j)
void longjmp(jmp_buf j, int i)
```

- **`setjmp`**：必须在 longjmp 之前调用；标识后续 longjmp 的**返回点**；把当前寄存器上下文、栈指针、PC 存入 `jmp_buf`，**返回 0**。**调用一次，返回一次或多次**。
- **`longjmp`**：在 setjmp 之后调用；从跳转缓冲 `j` 记住的 setjmp **再次返回**——这次返回 **i** 而非 0；恢复寄存器上下文（栈指针、基指针、PC），把 `%eax`（返回值）设为 i，跳到缓冲存的 PC。**调用一次，永不返回**。

### 示例：从深层嵌套直接返回

```c
jmp_buf buf;
void foo(void) { if (error1) longjmp(buf, 1); bar(); }
void bar(void) { if (error2) longjmp(buf, 2); }

int main() {
    switch(setjmp(buf)) {
    case 0: foo(); break;
    case 1: printf("Detected an error1 condition in foo\n"); break;
    case 2: printf("Detected an error2 condition in foo\n"); break;
    default: printf("Unknown error condition in foo\n");
    }
    exit(0);
}
```

完整流程（假设 `error1 = 0, error2 = 1`，错误发生在 bar 里）：

```
main 调 setjmp → 返回 0 → case 0 → foo()
  → foo: error1 假 → 调 bar()
    → bar: error2 真 → longjmp(buf, 2)   ← 瞬移！bar、foo 的栈帧直接丢弃
→ 回到 main 的 setjmp 那行，"再返回一次"，这次返回 2
→ switch case 2 → 打印 "Detected an error2 condition in foo"
```

注意 `bar()` 之后的代码、`foo()` 里 `bar()` 调用之后的代码都不会执行。

### 局限与危险

**只能 long jump 到"已被调用但尚未完成"的函数的运行环境**——被跳过的栈帧不再有效。反例：`P1` 调用 `P2`、`P2` 里 `setjmp(env)` 后**返回**，`P1` 再调 `P3`、`P3` 里 `longjmp(env, 1)` ——**不行**，因为 `P2` 已返回，其环境（栈帧）已失效，跳回去的"返回点"不再有意义。

**为什么危险**：longjmp 跳过的栈帧里可能有**未完成的清理工作**——malloc 的堆内存没 free、打开的文件没 close、锁没释放——这些清理代码永远不会执行。所以它只适合"出错时本来就要退出/重启"的错误恢复场景，不适合正常流程。

> 对比：`goto` 只能在函数**内部**跳转；`longjmp` **跨函数**跳转并丢弃中间所有栈帧，类似 C++ 的 `try/catch` 异常（setjmp ≈ try，longjmp ≈ throw）。

### 应用：ctrl-c 后自动重启

`sigsetjmp`/`siglongjmp` 组合：安装 SIGINT handler 调用 `siglongjmp(buf, 1)`；主程序 `sigsetjmp(buf, 1)` 非零分支打印 "restarting" 并继续 `processing...`——实现**程序被 ctrl-c 后重启自身**：

```c
/* restart.c */
sigjmp_buf buf;
void handler(int sig) {
    siglongjmp(buf, 1);            /* Ctrl-C → 直接跳回主程序的 sigsetjmp */
}
int main() {
    if (!sigsetjmp(buf, 1)) {
        Signal(SIGINT, handler);
        Sio_puts("starting\n");
    } else
        Sio_puts("restarting\n");  /* 每次 Ctrl-C 都从这继续 */
    while (1) {
        Sleep(1);
        Sio_puts("processing...\n");
    }
    exit(0);                       /* 控制永远到不了这里 */
}
```

```
greatwhite> ./restart
starting
processing...
processing...
processing...
restarting      ← 按了 Ctrl-C
processing...
...
```

handler 里不能"返回"到被中断的地方（那可能不安全），干脆用 longjmp 把主程序"重置"到安全点重启——这就是非局部跳转在信号处理里的典型用法。

## 总结

| 概念 | 要点 |
|---|---|
| **ECF 分层** | 异常（硬件+内核）/ 上下文切换（定时器+内核）/ 信号（内核+应用）/ 非局部跳转（C 库） |
| **异常** | 异步中断（返回下一条）/ 同步陷阱、故障、中止；异常表按号索引；页故障可恢复（重执行），无效引用发 SIGSEGV |
| **系统调用** | 陷阱；`%rax` 传号、参数走调用约定、返回 `%rax`；近 400 个，几乎都可能失败（−1 + errno） |
| **进程** | 运行中程序的实例；私有地址空间（虚拟内存）+ 逻辑控制流（上下文切换） |
| **上下文切换** | 保存/恢复寄存器 + 换页表；单核交错、多核并行；由内核调度 |
| **进程控制** | fork（两次返回）、exit（不返回）、wait/waitpid（收割）、execve（换程序） |
| **进程图** | 顶点=语句、边=先于；可行输出 = 拓扑排序；fork4 父续 / fork5 子续 |
| **僵尸** | 终止但未收割；父进程用 wait 收割，孤儿由 init 收 |
| **Shell** | read/evaluate 循环；前台 waitpid、后台打印 pid；后台僵尸需信号收割 |
| **信号** | 内核小消息（ID 1–30）；pending 不排队、blocked 可屏蔽（SIGKILL/SIGSTOP 除外）；进程组 + 键盘/`kill` 发送 |
| **安全处理** | G0–G5 指南；只调 async-signal-safe 函数（`write` 唯一安全输出，用 SIO 格式化） |
| **正确信号** | handler 循环收割；阻塞信号防竞态；`sigsuspend` 原子等待 |
| **非局部跳转** | setjmp/longjmp 打破调用返回纪律；仅限"已调用未完成"环境 |
