## 1. 并发编程为什么难

人脑倾向于**顺序**思考；时间的概念常误导人；要穷举计算机系统里所有可能的事件序列，至少容易出错、常常不可能。但并发**越来越必要**（多核、网络服务器），必须掌握。

**逻辑流 (logical flow)**：每个流是独立执行的指令序列，与时间上重叠的其他流并发执行。

---

## 2. 三种经典问题类

1. **竞争 (Races)**：程序正确性依赖系统其他部分的**任意调度决策**——例：飞机上最后一个座位给谁；
2. **死锁 (Deadlock)**：**不当的资源分配**使所有线程都无法前进——例：十字路口堵死；形式化定义：**等待一个永不可能发生的事件**（数学上不可能，不只是实际）；
3. **活锁 / 饥饿 / 公平 (Livelock / Starvation / Fairness)**：外部事件与/或系统调度决策使某些子任务无法前进——例：总有人插你的队。

**活锁 vs 死锁 vs 饥饿**（进度图视角）：死锁 = **wait-for 依赖成环**，环内线程都无法前进；活锁 = 线程在"推进"但没有朝目标进步；饥饿 = 有的线程不进步、有的在进步。**饥饿**：黄色必须给绿色让路，绿车川流不息 → 系统整体在进步，但个体无限期等待。

### 死锁实例：信号处理程序里用 printf

printf（及 fprintf/puts）内部实现**缓冲 I/O**，需要**锁**保护共享缓冲区。若信号处理程序里调用 printf，而信号恰好在主程序执行 printf、持有锁期间到达：

```c
void catch_child(int signo) {
    printf("Child exited!\n");   // 可能重入 printf！BAD！DEADLOCK！
    while (waitpid(-1, NULL, WNOHANG) > 0) continue;  // 收割所有子进程
}
```

主程序 `printf` 拿锁 → 信号中断 → handler 里的 `printf` 再要同一把锁 → **死锁**。测试程序（主程序 fork 100 万个子进程并 printf，handler 里 waitpid + printf）的 gdb 回溯清晰显示：`printf` 帧嵌套在 `sigchld` 帧之上，而 `sigchld` 又是被另一个 `printf` 中断的——**自死锁**。运行到约 3566 个子进程后 "and then, silence"。

## 3. 迭代服务器的缺陷与并发服务器

**迭代服务器 (iterative server)** 一次处理一个请求：Client 2 连接时，若 Client 1 还没处理完（用户去吃午饭），服务器阻塞在 Client 1 的 read——**Client 2 完全被晾着**。

**第二个客户端在哪里阻塞**：`connect` 返回（服务器端 TCP 管理器把请求排队——这叫 **TCP listen backlog**）；`rio_writen` 返回（内核缓冲输入数据）；**`rio_readlineb` 阻塞**（服务器还没为它写任何东西）。

**解法：并发服务器 (concurrent server)**——用多条**并发逻辑流**同时服务多个客户端。三种实现途径：

| 途径 | 交错方式 | 地址空间 | 本质 |
|---|---|---|---|
| **进程式** | 内核自动交错 | 每流**私有** | — |
| **事件式** | 程序员手动交错（I/O 多路复用） | 所有流**共享** | — |
| **线程式** | 内核自动交错 | 所有流**共享** | 进程式 + 事件式的混合 |

## 4. 进程式服务器

**思路**：为每个客户端 `fork` 一个子进程。

```c
int main(int argc, char **argv) {
    int listenfd, connfd;
    socklen_t clientlen;
    struct sockaddr_storage clientaddr;
    Signal(SIGCHLD, sigchld_handler);
    listenfd = Open_listenfd(argv[1]);
    while (1) {
        clientlen = sizeof(struct sockaddr_storage);
        connfd = Accept(listenfd, (SA *) &clientaddr, &clientlen);
        if (Fork() == 0) {          /* 子进程 */
            Close(listenfd);        /* 子进程关掉自己的监听 socket */
            echo(connfd);           /* 子进程服务客户端 */
            Close(connfd);          /* 子进程关闭连接 */
            exit(0);                /* 子进程退出 */
        }
        Close(connfd);              /* 父进程关闭已连接 socket（重要！）*/
    }
}

void sigchld_handler(int sig) {     /* 收割所有僵尸子进程 */
    while (waitpid(-1, 0, WNOHANG) > 0)
        ;
    return;
}
```

**为什么父进程必须 `Close(connfd)`**：fork 后父、子都有 `connfd` 副本，内核为每个 socket/打开文件维护**引用计数**——fork 后 `refcnt(connfd) = 2`，**连接要等 refcnt 归零才真正关闭**。父进程不关，连接永不关闭（泄漏）。同理子进程应关 `listenfd`。

**执行模型**：每个客户端由独立子进程处理，**子进程之间无共享状态**；监听服务器进程要**收割僵尸**避免致命内存泄漏。

**优点**：并发处理多连接；**干净的共享模型**（描述符：不共享；文件表：共享；全局变量：不共享）；简单直接。
**缺点**：进程控制有额外开销；进程间共享数据困难。

## 5. 事件式服务器

**思路**：服务器维护一组活跃连接（connfd 数组），循环：
1. 用 `select` 确定哪些描述符（connfd 或 listenfd）有**待处理输入**——pending 输入的到达就是一个**事件**；
2. 若 `listenfd` 有输入，`accept` 连接并把新 connfd 加入数组；
3. 服务**所有**有待处理输入的 connfd。

（`select` 的细节见教材。）

**优点**：单一逻辑控制流与地址空间；可用调试器单步；无进程/线程控制开销——**高性能 Web 服务器与搜索引擎的首选设计**（Node.js、nginx、Tornado）。
**缺点**：编码比进程式/线程式复杂得多；难以提供细粒度并发（如处理部分 HTTP 请求头）；**无法利用多核**（单线程控制流）。

## 6. 线程：进程的另一种视图

**传统视图**：进程 = 进程上下文 + 代码/数据/栈。
**交替视图**：进程 = **线程 (thread)** + 代码/数据/内核上下文——线程上下文 = 数据寄存器、条件码、栈指针 (SP)、程序计数器 (PC)。

**多线程进程**：多个线程与一个进程关联，每个线程：
- 有自己的**逻辑控制流**；
- **共享**同一份代码、数据与内核上下文；
- 有自己的**栈**（局部变量），**但不受其他线程保护**（任何线程可读写任何线程的栈！）；
- 有自己的**线程 ID (TID)**。

**逻辑视图**：同进程的线程形成**对等 (peer) 池**——不同于进程的树形层级。

**并发 (concurrent)**：两个线程的流在**时间上重叠**即并发，否则顺序。单核用**时间片**模拟并行，多核有**真并行**。

**线程 vs 进程**：相似处——各有逻辑控制流、可并发（可能在不同核）、会被上下文切换。不同处——**线程共享所有代码与数据**（除局部栈），进程（通常）不共享；**线程更廉价**：Linux 上创建+回收进程约 20K cycles，线程约 10K cycles 或更少。

**线程 vs 信号**：信号处理程序与常规程序**共享状态**（含栈）；它**中断**常规执行流（意外的过程调用，完成后返回）；**不是对等线程**；同步形式有限（主程序只能阻塞/解除阻塞信号、为信号暂停）。

**Pthreads 接口**（约 60 个函数）：`pthread_create` ↔ fork、`pthread_join` ↔ waitpid、`pthread_self` ↔ getpid、`pthread_exit` ↔ exit、`pthread_mutex_lock/unlock`（无进程对应物）。

**Pthreads "hello, world"**：

```c
#include "csapp.h"
void *thread(void *vargp);

int main(int argc, char** argv) {
    pthread_t tid;
    Pthread_create(&tid, NULL, thread, NULL);  // 线程 ID、属性(常 NULL)、线程例程、参数(void *)
    Pthread_join(tid, NULL);                   // 等待对等线程终止（返回值经 void **）
    return 0;
}

void *thread(void *vargp) {
    printf("Hello, world!\n");
    return NULL;
}
```

执行序列有**许多种可能**（`pthread_join` 等待与否均可）；注意 `exit()` 终止主线程时**任何对等线程也一起终止**。

## 7. 线程式服务器

**思路**：与进程式几乎一样，但用线程替代进程。

```c
/* 主例程 */
int main(int argc, char **argv) {
    int listenfd, *connfdp;
    socklen_t clientlen;
    struct sockaddr_storage clientaddr;
    pthread_t tid;
    listenfd = Open_listenfd(argv[1]);
    while (1) {
        clientlen = sizeof(struct sockaddr_storage);
        connfdp = Malloc(sizeof(int));            /* 注意用 Malloc()！（但这里没 Free） */
        *connfdp = Accept(listenfd, (SA *) &clientaddr, &clientlen);
        Pthread_create(&tid, NULL, thread, connfdp);  /* 每个客户端一个新线程 */
    }
    return 0;
}

/* 线程例程 */
void *thread(void *vargp) {
    int connfd = *((int *)vargp);
    Pthread_detach(pthread_self());   /* 分离模式：独立运行，终止时内核自动回收 */
    Free(vargp);                      /* 释放存放 connfd 的存储 */
    echo(connfd);
    Close(connfd);
    return NULL;
}
```

**要点**：
- 每个线程必须运行在 **detached（分离）** 模式避免内存泄漏——任一时刻线程要么 **joinable**（可被其他线程收割/杀死，必须 `pthread_join` 释放资源）要么 **detached**（资源终止时自动回收，不可被收割/杀死）；**默认是 joinable**，用 `pthread_detach(pthread_self())` 转为 detached；
- 传参用 `Malloc` 而非传主线程栈地址——**生产者-消费者模型：主线程（生产者）分配、线程（消费者）释放**；
- 线程共享除 TID 外的所有进程状态，每个线程有独立栈。

**意外共享的陷阱**：不要传 `&connfd`（主线程栈上的局部变量）——主线程循环里 `connfd` 被反复覆盖，**所有线程的 `vargp` 指向同一个位置**，读取到的是同一（后来者）值。实验（主线程 `for (i...) Pthread_create(..., &i)`）：**单核笔记本上没 race**（创建比循环快），**多核服务器上值乱飞**（有的 bin 0 个、有的 2 个以上）——race 概率低但非零，**极难靠测试发现**。

**优点**：线程间**易共享数据结构**（日志、文件缓存）；比进程高效。
**缺点**：**意外共享引入微妙、难复现的错误**——"数据共享的容易程度既是线程最大的优点也是最大的缺点"；难以知道哪些数据共享、哪些私有；难以靠测试发现。

**三种并发途径总结**：进程式——难共享资源、易避免意外共享、增删客户端开销高；事件式——繁琐且底层、调度完全可控、开销极低、无法细粒度并发、不用多核；线程式——共享资源"也许太容易"、中等开销、对调度策略控制少、事件顺序不可复现所以难调试。

## 8. 线程传参：三种方式与一个陷阱

1. **Malloc/free**：生产者 malloc 空间、传指针给 `pthread_create`；消费者解引用后 free——**总是可行**，传大数据结构时必要；
2. **int/long 的 cast**：生产者把 int/long 转型为 `void *`，消费者转回——小数据（一个数）可行；
3. **指向栈槽的指针（错误！）**：生产者传**自己栈上**变量的地址——消费者解引用时该槽可能已被改写（上一讲的 race）。

正例：传 `&hist[i]`（每个线程得到唯一指针）、传 `(void *)i`（唯一数组索引值）、`Malloc` + 线程内 `free`。反例：传 `&i`（所有线程拿到同一指针、读同一变量）→ 数据竞争。

## 9. 共享变量

**问题**：线程化 C 程序里哪些变量是共享的？答案**不是**简单的"全局变量共享、栈变量私有"。

**定义**：变量 $x$ 是**共享的 (shared)** 当且仅当**多个线程引用 $x$ 的某个实例**。

需要回答三个问题：线程的内存模型是什么？变量实例如何映射到内存？有多少线程可能引用这些实例？

**变量实例到内存的映射**：
- **全局变量**（函数外声明）：虚拟内存里**恰好一个实例**；
- **局部自动变量**（函数内、无 static）：**每个线程栈一个实例**；
- **局部 static 变量**（函数内、static）：虚拟内存里**恰好一个实例**；
- **errno 特殊**：声明在函数外，但**每个线程栈一个实例**。

**sharing.c 分析**：全局 `ptr`（1 实例）、`cnt`（static，1 实例）、`msgs`（main 的自动变量，1 实例）→ **共享**；`i`（main 的自动变量）与 `myid`（各线程的自动变量，每线程 1 实例）→ **不共享**。共享判据是"是否有多个线程引用**同一实例**"。

**线程内存模型——概念 vs 实际**：概念上每线程有私有上下文；**实际**上数据分离并不严格强制——寄存器值真分离且受保护，但**任何线程都能读写任何其他线程的栈**。概念模型与实际模型的落差是困惑和错误的来源。

## 10. 数据竞争与坏计数

共享变量方便，但冒**数据竞争**与同步错误的风险。经典例子（`badcnt`）：两个线程各把共享 `cnt` 加 `niters` 次，期望 `2*niters`，实际可能 **BOOM**。

`cnt++` 的汇编是**三条指令**：`Li: Load cnt`（`movq cnt(%rip),%rdx`）、`Ui: Update cnt`（`addq \$1, %rdx`）、`Si: Store cnt`（`movq %rdx, cnt(%rip)`）。

**关键思想：任何指令交错都可能发生，有些给出意外结果。** 例：T1 完成 L1/U1 后，T2 完成 L2（读到旧值 0），T1 S1 写回 1，T2 U2/S2 也写回 1——**两次递增结果却是 1**。另一个错误顺序同样 `Oops!`。

## 11. 进度图：并发执行的几何

**进度图 (progress graph)** 刻画并发线程的离散执行状态空间：
- 每个**轴**对应一个线程指令的**顺序**；
- 每个**点**对应一个可能的执行状态 $(Inst_1, Inst_2)$——如 $(L_1, S_2)$ 表示线程 1 已完成 $L_1$、线程 2 已完成 $S_2$；
- **轨迹 (trajectory)**：合法状态转移的序列，描述一次可能的并发执行（如 $H_1, L_1, U_1, H_2, L_2, S_1, T_1, U_2, S_2, T_2$）。

**临界区与不安全区域**：对共享变量 `cnt` 而言，$L, U, S$ 构成一个**临界区 (critical section)**——其中的指令**不应被交错**；发生这种交错的**状态集合**构成**不安全区域 (unsafe region)**。

**定义**：轨迹是**安全 (safe)** 的当且仅当它不进入任何不安全区域；轨迹**正确**（wrt cnt）当且仅当它安全。

## 12. 互斥锁

**问题**：如何保证安全轨迹？——**同步**线程执行，使它们永远不可能走出不安全轨迹：**保证每个临界区互斥访问**。

**互斥锁 (MUTual EXclusion, mutex)**：不透明对象，要么 locked 要么 unlocked（布尔值，但不能对它做运算；初始为 unlocked）。两个操作：
- `lock(m)`：若 m 当前未锁，锁上并返回；否则**等待**到它解锁，再重试；
- `unlock(m)`：只能由**锁住它的那段代码**调用；把 m 改为 unlocked。

```c
static unsigned long cnt = 0;
static pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
void *incr_thread(void *arg) {
    unsigned long i;
    unsigned long niters = (unsigned long) arg;
    for (i = 0; i < niters; i++) {
        pthread_mutex_lock(&lock);
        cnt++;
        pthread_mutex_unlock(&lock);
    }
}
```

**为什么 mutex 有效**：`lock`/`unlock` 包围临界区提供互斥访问；mutex 不变量（同一时刻至多一个线程持有锁）创建一个**禁区 (forbidden region)**，它**包围不安全区域**且任何轨迹都无法进入——于是不安全轨迹被排除。

**代价**：无锁 0.48s，加锁 15s——**约 30 倍慢**（对 `cnt++` 这种微小临界区，锁开销远大于操作本身）。

## 13. 信号量

**信号量 (semaphore)**：mutex 的**推广**。无符号整数值（不能做运算），创建时设某个 $\ge 0$ 的初值；两个操作：
- **P(s)**（"ProLaag"，荷兰语"尝试减少"）：若 $s$ 为 0，等待某个 V 操作发生；然后 $s$ 减 1 并返回；
- **V(s)**（"Verhogen"，荷兰语"增加"）：$s$ 加 1；若有线程在 P 内等待，唤醒其中一个。

**与 mutex 的关键区别**：**不要求 P 在 V 之前调用**，任何线程可 P、任何线程可 V，无顺序要求。

**C 接口**（Pthreads 函数）：

```c
#include <semaphore.h>
int sem_wait(sem_t *s);   /* P(s) */
int sem_post(sem_t *s);   /* V(s) */
int sem_init(sem_t *s, int pshared, unsigned int val);  /* 初值 val；pshared 通常传 0 */
```

**用信号量实现互斥**（初值 1 的二元信号量）：`sem_wait`/`sem_post` 包住临界区即可（与 mutex 用法相同）。**代价比 mutex 更慢**（27.6s）——**能用 mutex 就别用信号量**。

**实现**：mutex 与信号量的实现"可疑地相似"——本质都是**一条硬件原子指令**（`lock xadd` 等）加一段睡眠等待路径（约 30 条机器指令 + 一次系统调用）。细节属 OS/体系结构课程。

## 14. 原子内存操作

**原子内存操作**是特殊的硬件指令："test-and-set"、"compare-and-swap"、"exchange-and-add"…它们在内存上做**读-改-写**，硬件保证无数据竞争——**用于实现 mutex、信号量等**。

直接用它们不是更好吗——尤其是只想递增计数器时？C11 的 `_Atomic` 类型：

```c
static _Atomic unsigned long cnt = 0;
void *incr_thread(void *arg) {
    unsigned long i;
    unsigned long niters = (unsigned long) arg;
    for (i = 0; i < niters; i++) {
        cnt++;
    }
}
```

汇编对比：普通 `cnt++` 是 load/add/store 三条；`_Atomic` 的 `cnt++` 变成**一条 `lock addq \$1, cnt(%rip)`**——硬件保证执行时等待其他线程的同类操作（经缓存访问协议）。x86 有大量原子操作；**传统 RISC 没有这么慷慨**（要写循环 + 两条特殊访存指令 + ADD）。

**代价**：3.41s（比锁快，比无锁慢约 7 倍）。**注意**：硬件可能不提供你需要的操作；原子操作**难用对**（后续课程）。

**三种同步方式对比**：无锁（错误但快）0.48s；mutex 15s；semaphore 27.6s；atomic 3.41s。

**同步基础总结**：小心访问共享变量避免数据竞争——先搞清楚**哪些变量是共享的**；能避免共享就避免；能避免多线程写就避免。Mutex 有用但慢（还会带来新问题）；别用信号量充当 mutex（更慢）；原子操作方便但硬件未必提供所需操作。

## 15. 竞争不一定能靠互斥解决

**有些竞争可以用互斥解决**（counter 竞争，加锁即可），**有些不能**：

**传 `&i` 的竞争**（主线程 `for (i...) Pthread_create(..., &i)`）：等线程读到 `i` 时主线程可能已改它。**不能用 mutex 修**——mutex 必须在 `pthread_create` 之前就被新线程锁住，而这做不到（线程还不存在）。两种修法：
- **复制数据**：传 `(void *)i`（值拷贝，主线程改 `i` 不影响已拷贝的值）；
- **用信号量**：`sem_init(&sem, 0, 0)`；每 `pthread_create` 后 `sem_wait(&sem)`，线程读 `i` 后 `sem_post(&sem)`——保证主线程在 `i++` 前等线程读完。**mutex 做不到这点**：线程只能 unlock 自己锁过的 mutex。

**不涉及线程的竞争：TOCTOU**。`access("myfile.txt", R_OK)` 检查后、`fopen` 使用前，文件可能被别的程序删掉——**check-to-use (TOCTOU) 竞争**。修法：**别检查，直接用**（`fopen` 失败再处理）：如果文件在 fopen 前被删，失败检查会正确处理；如果 fopen 后删除，打开期间文件仍存在。讲义原话：玩了近 30 年 Unix，从没见过 `access()` 用对的地方——它几乎和 `gets()` 一样是"这里有 bug"的旗帜。

**信号处理程序的竞争**：子进程太快结束，`SIGCHLD` 在 `add_job(pid, argv)` 之前到达 → handler 想更新一条**还不存在**的记录。修法：从 fork 前到 `add_job` 完成之间**阻塞 SIGCHLD**。

**竞争消除三法**：① **不共享状态**（如用 malloc 为每个线程生成独立参数副本）；② **别先检查后用**（直接用，看是否失败）；③ **用同步原语**（选哪种取决于情况）。

## 16. 死锁

**死锁 (deadlock)**：程序等待一个**永远不可能发生**的事件（数学上的不可能）。最常见形式：线程 A 等线程 B 做某事，线程 B 等线程 A 做某事，**谁都无法前进**。

**错误加锁顺序导致死锁**：

```c
/* thread_1 */
pthread_mutex_lock(&mA);
pthread_mutex_lock(&mB);
/* ... */
pthread_mutex_unlock(&mA);
pthread_mutex_unlock(&mB);

/* thread_2 */
pthread_mutex_lock(&mB);   /* 与 thread_1 加锁顺序相反！ */
pthread_mutex_lock(&mA);
/* ... */
pthread_mutex_unlock(&mB);
pthread_mutex_unlock(&mA);
```

**进度图可视化**：两个 mutex 各产生一个禁区；两禁区**相交**形成**死锁区域**；进入死锁区域的任何轨迹最终都会到达**死锁状态**——该点既不能向上也不能向右（双方都在等对方释放锁）。其他轨迹可能侥幸绕过——**轨迹差异使死锁 bug 非确定**（不总是显现，极难调试）。

**修法：一致的加锁顺序**（都先 `mA` 后 `mB`）——任意时刻总可以"向上或向右移动"。注意：**解锁顺序不一致没关系**，只有**加锁顺序**会造成死锁。

## 17. 信号量作为事件与队列

信号量不只做互斥：初值 0 时它能把"事件发生"信号化，还能组织生产者-消费者队列。这一节给事件信号量与队列两种典型用法。

### 事件信号量

信号量初值为 0 时，**P 等待一个事件、V 发出事件**。例子：线程把 `&myid` 存入 `pointers[myid]`，主线程 sleep 1 秒后读取——**需要同步**：

```c
#define N 4
long *pointers[N];
sem_t ready[N];     /* 每个线程一个"就绪"信号量 */
sem_t finish;       /* 主线程发出的"结束"信号量 */

void *thread(void *vargp) {
    long myid = (long) vargp;
    pointers[myid] = &myid;
    sem_post(&ready[myid]);   /* 告诉主线程：我已就绪 */
    sem_wait(&finish);        /* 等主线程读完所有值 */
    return NULL;
}

int main(void) {
    long i;
    pthread_t tids[N];
    Sem_init(&finish, 0, 0);
    for (i = 0; i < N; i++) {
        Sem_init(&ready[i], 0, 0);
        Pthread_create(&tids[i], NULL, thread, (void *) i);
    }
    for (i = 0; i < N; i++) {
        sem_wait(&ready[i]);              /* 等第 i 个线程就绪 */
        printf("Thread #%ld has local value %ld\n", i, *pointers[i]);
    }
    for (i = 0; i < N; i++)
        sem_post(&finish);                /* 放行所有线程 */
    for (i = 0; i < N; i++)
        Pthread_join(tids[i], NULL);
    return 0;
}
```

### 生产者-消费者队列

常见同步模式：**生产者**等空槽、插入队列、通知消费者；**消费者**等条目、取出、通知生产者。实例：多媒体处理（生产帧、渲染）、事件驱动 GUI（鼠标/键盘事件入队、绘制线程取事件）。

**1 元素队列**：维护两个信号量 `full` 和 `empty`。多生产者/多消费者：生产者之间争 `empty`，消费者之间争 `full`。

```
P(&shared.empty);            P(&shared.full);
shared.buf = item;           item = shared.buf;
V(&shared.full);             V(&shared.empty);
```

**n 元素队列**：需要一个 **mutex + 两个计数信号量**——`mutex` 保护队列内部的互斥访问，`slots` 计数空槽，`items` 计数条目（信号量值 > 1，最多 n）。

## 18. 读者-写者问题与饥饿

**问题陈述**：**读者线程**只读对象；**写者线程**修改对象（读/写访问）；**写者必须独占访问**；**读者数量不限**。现实实例：在线机票预订系统、多线程缓存 Web 代理。

**Pthreads 读写锁**：数据类型 `pthread_rwlock_t`；操作 `pthread_rwlock_rdlock`（读锁）、`pthread_rwlock_wrlock`（写锁）、`pthread_rwlock_unlock`（释放任一锁）。**必须正确使用**——由程序员决定哪些操作需要读锁、哪些需要写锁。

**饥饿**：线程**在不可接受的长时间内没有前进**（与死锁不同，它最终可能解脱）；"不可接受地长"取决于应用。场景：线程 1 持读锁、线程 2 等写锁、线程 3 想取读锁——若 R2 立即拿读锁，**读者川流不息 → 写者永远等**；若写者总是尽快拿锁，**写者川流不息 → 读者等**。

**公平 (fair)**：保证无饥饿的算法——公平读写锁让每个等待者按**先来先服务 (FCFS)** 获得锁（多个读者可同时获锁）。**公平更复杂**，且可能让**所有线程都变慢**（如"锁护卫问题" lock convoy）。

## 19. 线程安全 API 设计

**定义**：函数是**线程安全 (thread-safe)** 的，当且仅当从多个并发线程**反复调用**时总是产生正确结果。

**四类线程不安全函数**：

| 类 | 特征 | 例 | 能否加锁修复 | 修法 |
|---|---|---|---|---|
| **1** | 内部共享状态、无锁 | 你自己实现的 malloc | ✅ 加锁即可 | 内部加锁 |
| **2** | 跨多次调用保持内部状态 | `rand`（static `next`） | ❌（锁不住"调用序列"） | 状态作参数（`rand_r`） |
| **3** | 返回指向 static 变量的指针 | `itoa`、`strtok` | ❌（返回值使用期间被别线程覆盖） | 调用者提供空间 |
| **4** | 调用上述任何函数 | — | 传递性地不安全 | 只调用安全函数 |

**类 1 例**：`malloc`/`realloc`/`free`——你的实现多线程调用会崩，C 库实现有内部锁不会。加锁当然拖慢速度。
**类 2 例**：`rand` 靠 static `next` 维护状态；两个线程并发调用得到的结果不同于单线程顺序调用。修法（`rand_r`）：状态作为参数传入——需要 **API 变更**，调用者负责分配状态空间。
**类 3 例**：`itoa` 返回 static 缓冲区指针；加锁没用（另一个线程的调用会覆盖缓冲区，与"使用返回值"竞争）。修法：`itoa_r(x, buf, bufsz)` 让调用者提供空间——也需要 API 变更（对调用者可能不便：不知道要多大空间）。
**类 4**：任何在内部使用 1/2/3 类函数的函数，不安全程度与之一致，且**传递**；唯一修法是改用安全函数（可能涉及 API 变更）。

**库函数现状**：多数 ISO C 库函数线程安全（`malloc`/`free`/`printf`/`scanf`）；例外 `strtok`、`rand`、`asctime` 等。许多老 Unix 库函数不安全，**通常有安全替代**：`asctime`→`strftime`、`ctime`→`strftime`、`localtime`→`strftime`、`gethostbyname`→`getaddrinfo`、`gethostbyaddr`→`getnameinfo`、`inet_ntoa`→`getnameinfo`、`rand`→`rand_r`（注：C 库随机数生成器都老旧且不强，建议用现代 CSPRNG）。

**可重入 (reentrant)**：函数**不访问任何共享变量**时称可重入——线程安全函数的**重要子集**；**不需要任何同步操作**；类 2 函数**唯一**的线程安全修法就是让它可重入（如 `rand_r`）。

**线程/信号交互**：许多库函数用 **lock-and-copy** 实现线程安全（`malloc` 保护空闲链表、`fprintf`/`printf`/`puts` 防止输出交错、`snprintf` 内部 malloc）。**持有锁时被打断可以**——只要信号处理程序**自己不用这些函数**。若信号恰在库函数持锁时到达、handler 调用同一（或相关）库函数——**死锁**：handler 拿不到锁无法前进，主程序等 handler 完成也无法前进。

> **关键点**：线程之间是**对称**的并发关系；信号处理是**非对称**的（中断方与被中断方地位完全不同）——这正是 printf 死锁示例（§2）的根源，也是"信号处理程序中只做异步信号安全操作"这条纪律的由来。
