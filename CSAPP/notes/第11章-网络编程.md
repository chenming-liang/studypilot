## 1. 从局域网到互联网

**计算机网络的本质**：一个按地理邻近组织的盒子与线缆的层级系统。

- **LAN（局域网）**：覆盖一栋建筑或校园——以太网 (Ethernet) 是最突出的例子；
- **WAN（广域网）**：覆盖国家或世界——通常是高速点对点（多为光纤）链路；
- 还有 SAN（存储区域网）、MAN（城域网）等；
- **互联网 (internet，小写)**：一组互连的网络；**全球 IP 互联网 (Internet，大写)** 是最著名的实例。

**构建层级**：

1. **以太网段 (Ethernet segment)**：一组主机用双绞线连到 **hub**（集线器），覆盖一个房间/一层楼。每个以太网适配器有唯一 48 位 **MAC 地址**（如 `00:16:ea:e3:54:e6`）。
2. **桥接以太网段 (bridged Ethernet segment)**：**bridge（网桥）** 学会哪个端口可达哪些主机，选择性地在端口间转发帧——覆盖一栋建筑/校园。
3. **互联网 (internet)**：多个不兼容的 LAN 由专门的计算机——**router（路由器）** 物理连接起来。LAN 1 和 LAN 2 可能完全不同、完全不兼容（以太网、光纤通道、802.11、T1、DSL…）。
4. **互联网的逻辑结构**：网络的临时互连，无特定拓扑；路由器与链路容量差异巨大；包从源到目标**逐跳 (hop)** 穿过网络，不同包可走不同路径。

**互联网协议 (internet protocol)** 解决"如何在互不兼容的网络间传比特"：**每台主机和路由器上运行的协议软件**——协议是一组规则，规定主机/路由器在跨网络传输数据时如何协作，抹平不同网络的差异。

一个互联网协议做两件事：
- **命名方案**：定义统一的**主机地址格式**，每台主机/路由器至少分配一个唯一互联网地址；
- **投递机制**：定义标准传输单元——**包 (packet)**，由**头部 (header)**（含包大小、源/目的地址等信息）和**载荷 (payload)**（源主机发送的数据位）组成。

**为什么要包 (packet switching)**：把数据拆成小片传输。优点：包未收到可要求重发；易处理损坏/乱序数据；不同包可走不同路径适应网络变化。缺点：增加总传输字节数；对低延迟要求（如视频通话）不适合。

## 2. 协议、分层与封装

网络协议栈按**分层**组织（以 TCP/IP 为例）：应用层 (application) → 传输层 (transport, TCP) → 网络层 (network, IP) → 链路层 (link, Ethernet) → 物理层 (physical)。发送时每层为数据加自己的**头部**：

| 层 | 数据单元 | 头部 |
|---|---|---|
| 应用 | message（消息） | — |
| 传输 | segment（段） | $H_t$ |
| 网络 | datagram（数据报） | $H_t + H_n$ |
| 链路 | frame（帧） | $H_t + H_n + H_l$ |

**封装 (encapsulation)**：源端逐层加头，目的端逐层剥头。讲义还强调一堆被略过的问题：不同网络最大帧大小不同怎么办（分段）？路由器怎么知道往哪转发？拓扑变化时怎么更新？包丢了怎么办？——这些属于**计算机网络**这门学科。

**全球 IP 互联网**基于 **TCP/IP 协议族**：
- **IP (Internet Protocol)**：提供基本命名方案和主机到主机的**不可靠**数据报投递；
- **UDP (User Datagram Protocol)**：基于 IP，提供进程到进程的**不可靠**数据报投递；
- **TCP (Transmission Control Protocol)**：基于 IP，提供进程到进程、基于连接的**可靠字节流**。

应用通过 **Unix 文件 I/O + sockets 接口**访问网络：客户端/服务器都是用户代码用 sockets 接口（系统调用）与内核 TCP/IP 栈交互，硬件接口处理物理收发。

## 4. IP 地址与域名系统

这一节讲"定位主机"的两个命名系统：32 位 IP 地址（含字节序、IPv4/IPv6）与分层的域名系统 DNS，最后给出客户-服务器事务模型作为连接的舞台。

### IP 地址

**IP 地址结构**（IPv4，32 位）：

```c
/* Internet address structure */
struct in_addr {
    uint32_t s_addr; /* network byte order (big-endian) */
};
```

- IP 地址**总是以网络字节序（大端）存储在内存中**——凡是在包头部里跨机器传输的整数都如此（比如端口号）；
- **点分十进制表示**：每字节用十进制、以点分隔，如 `0x8002C2F2 = 128.2.194.242`；
- 用 `getaddrinfo`/`getnameinfo` 在 IP 地址与点分十进制之间转换。

**IPv4 vs IPv6**：IPv4 用 32 位地址（1981 年制定，~1990 年起已知不够用）；IPv6 用 128 位地址（1996 年制定，`2001:0db8:...`），意在取代 IPv4，但因必须更换路由器而普及缓慢。应用程序员大多**不用关心**——sockets API 让代码无缝适配两者。

### 域名与 DNS

域名层级：根（unnamed）→ 顶级域（`.com`/`.edu`/`.net`/`.gov`）→ 二级域（`cmu`/`berkeley`/`mit`）→ 三级域（`cs`/`ece`）……

**DNS (Domain Naming System)**：全球分布式数据库，维护 IP 地址与域名之间的映射；程序员可把它看作数百万条**主机条目 (host entry)** 的集合，每条定义一组域名与 IP 的映射。

**DNS 映射的性质**（可用 `nslookup` 探索）：
- `localhost` 总是映射到回环地址 `127.0.0.1`（用 `hostname` 查本机真实域名）；
- **一对一**：`whaleshark.ics.cs.cmu.edu → 128.2.210.175`；
- **多域名 → 同一 IP**：`cs.mit.edu` 与 `eecs.mit.edu` 都指向 `18.25.0.23`（反向也可查）；
- **多域名 → 多 IP**：`www.twitter.com` 一次返回多个地址（负载均衡）；
- **有效域名可能不映射任何 IP**：`ics.cs.cmu.edu` 无地址。

### 客户端-服务器事务模型

大多数网络应用基于**客户端-服务器模型**：服务器管理某种**资源**，通过操作资源为客户提供服务；服务器由客户端请求**激活**（自动售货机类比）。事务四步：① 客户端发请求 → ② 服务器处理请求 → ③ 服务器发响应 → ④ 客户端处理响应。注意：客户端和服务器是**进程**（可运行在同一或不同主机上）。

## 5. 连接：socket 与端口

客户端与服务器最常通过 **TCP 连接**交换字节流。每个连接：
- **点对点 (point-to-point)**：连接一对进程；
- **全双工 (full-duplex)**：数据可同时双向流动；
- **可靠 (reliable)**：源发送的字节流最终被目的以**相同顺序**收到。

**socket** 是连接的端点；**socket 地址**是 `IP 地址 : 端口` 对。**端口 (port)** 是标识进程的 16 位整数：
- **临时端口 (ephemeral port)**：客户端内核发起连接请求时自动分配；
- **知名端口 (well-known port)**：与服务绑定（Web 服务器 = 80）。

知名服务与端口：echo 7、ftp 21、ssh 22、smtp 25、http 80、https 443；映射表在每台 Linux 机的 `/etc/services`。

**连接的唯一标识**：连接由端点的 socket 地址对（**socket pair**）唯一确定：
$$(\text{cliaddr}:\text{cliport},\ \text{servaddr}:\text{servport})$$
例如客户端 `128.2.194.242:51213` 连服务器 `208.216.181.15:80` → socket pair `(128.2.194.242:51213, 208.216.181.15:80)`。端口在主机内区分进程：同一主机上 Web 服务器（80）与 echo 服务器（7）并行不悖。

**对应用而言，socket 就是文件描述符**——读/写网络就是读/写 fd，这让你能复用已有的文件 I/O 代码与接口。socket I/O 与普通文件 I/O 的唯一区别是**如何"打开"socket 描述符**。

## 6. Sockets 接口

Sockets 接口是一组与 Unix I/O 配合构建网络应用的系统级函数（80 年代初随伯克利 Unix 诞生，如今全平台可用）。

### getaddrinfo：主机与服务转换

```c
int getaddrinfo(const char *host,             /* 主机名或地址 */
                const char *service,          /* 端口或服务名 */
                const struct addrinfo *hints, /* 输入参数 */
                struct addrinfo **result);    /* 输出链表 */
void freeaddrinfo(struct addrinfo *result);
const char *gai_strerror(int errcode);
```

- 现代方式：把主机名/主机地址/端口/服务名的字符串形式转成 socket 地址结构；取代过时的 `gethostbyname`/`getservbyname`；
- 优点：**可重入**（线程安全）、可写**协议无关**的移植代码、同时支持 IPv4/IPv6；缺点：较复杂（但少数用法模式就够用）；
- 返回的 `result` 指向 `addrinfo` 结构**链表**（每个含 `ai_addr` 指向对应 socket 地址结构）；客户端沿链表逐个试 `socket`+`connect`，服务器逐个试 `socket`+`bind`，直到成功。

### socket：创建描述符

```c
int socket(int domain, int type, int protocol);
int clientfd = socket(AF_INET, SOCK_STREAM, 0);
```

`AF_INET` = 32 位 IPv4 地址；`SOCK_STREAM` = 可靠 (TCP) 连接的端点。最佳实践是直接用 `getaddrinfo` 的结果（`ai_family`/`ai_socktype`/`ai_protocol`）——这样无需知道具体协议。

### bind：服务器绑定地址

```c
int bind(int sockfd, SA *addr, socklen_t addrlen);
```

服务器请求内核把**服务器的 socket 地址**关联到 socket 描述符；此后读 `sockfd` 得到发到 `addr` 连接的字节，写 `sockfd` 沿 `addr` 端点连接传输。约定 `typedef struct sockaddr SA;`。最佳实践：用 `getaddrinfo` 提供 `addr`/`addrlen`，逐个地址尝试直到 `bind` 成功（配合 `SO_REUSEADDR` 消除 "Address already in use" 错误）。

### listen：变成监听 socket

```c
int listen(int sockfd, int backlog);
```

内核默认认为 `socket` 创建的描述符是**活跃 socket**（客户端那端）。服务器调 `listen` 告知内核此描述符用于服务端：把 `sockfd` 从活跃 socket 转为**监听 socket (listening socket)**，可接受客户端的连接请求。`backlog` 是内核在开始拒绝请求前可排队未处理连接请求数的提示（默认约 128）。

### accept：接受连接

```c
int accept(int listenfd, SA *addr, int *addrlen);
```

服务器调用 `accept` 等待连接请求到达 `listenfd`；请求到达后，把客户端 socket 地址填入 `addr`、大小填入 `addrlen`，返回**已连接描述符 (connfd)**——用 Unix I/O 例程与客户端通信就靠它。

### connect：客户端建立连接

```c
int connect(int clientfd, SA *addr, socklen_t addrlen);
```

尝试与 `addr` 处的服务器建立连接；成功后 `clientfd` 可读可写。结果连接由 socket pair $(x:y,\ \text{addr.sin\_addr}:\text{addr.sin\_port})$ 刻画——$x$ 是客户端地址，$y$ 是唯一标识客户端进程的临时端口。

### connect/accept 三幕剧

1. 服务器阻塞在 `accept`，在监听描述符 `listenfd` 上等待连接请求；
2. 客户端调用并阻塞在 `connect`，发出连接请求；
3. 服务器从 `accept` 返回 `connfd`，客户端从 `connect` 返回——连接在 `clientfd` 与 `connfd` 之间建立。

### 辅助函数 open_clientfd / open_listenfd

CS:APP 包装了上述模式：`open_clientfd(hostname, port)`（`socket`+`connect` 逐个地址尝试）、`open_listenfd(port)`（`socket`+`bind`+`listen`，`AI_PASSIVE` 表示监听任意 IP 地址）。**两者都独立于任何特定 IP 版本**——协议无关的典范。

## 7. 监听与连接描述符

- **监听描述符 (listening descriptor)**：客户端连接请求的端点，**创建一次、存续服务器整个生命周期**；
- **已连接描述符 (connected descriptor)**：客户端与服务器之间连接的端点，**每次接受连接请求创建新描述符**，只存续到服务完该客户端。

**为什么区分两者**：让服务器可以**并发**地同时与多个客户端连接通信——例如每收到一个新请求就 `fork` 一个子进程处理。

## 8. 测试服务器：telnet

`telnet <host> <portnumber>` 创建与 `host` 上监听 `portnumber` 的服务器的连接——对传输 ASCII 字符串的服务器（echo 服务器、Web 服务器、邮件服务器）是**宝贵的测试工具**。示例：`telnet whaleshark.ics.cs.cmu.edu 15213` 连上 echo 服务器，逐行得到回显，`^]` + `quit` 断开。

## 9. HTTP 协议

**HTTP (HyperText Transfer Protocol)**：客户端与服务器交换 Web 内容的协议。流程：建立 TCP 连接 → 客户端请求内容 → 服务器响应内容 →（最终）关闭连接。当前版本 HTTP/3，但 HTTP/1.1 与 HTTP/2 仍广泛使用。

**Web 内容**：带 **MIME 类型**的字节序列。常见 MIME：`text/html`（HTML 文档）、`text/plain`（纯文本）、`image/gif`/`image/png`/`image/jpeg`（图像）。

**静态 vs 动态内容**：
- **静态内容**：存储在文件中、响应请求时取回（HTML 文件、图片、音频、JS 程序）；请求指明哪个内容文件；
- **动态内容**：响应请求时**现做**（服务器代表客户端执行的程序产生的输出）；请求指明含可执行代码的文件。

**URL**：文件的唯一名字，如 `http://www.cmu.edu:80/index.html`。
- 客户端用**前缀** `http://www.cmu.edu:80` 推断：用什么协议（HTTP）、服务器在哪（www.cmu.edu）、监听哪个端口（80）；
- 服务器用**后缀** `/index.html`：判断静态/动态内容（无硬性规则；惯例是可执行程序放在 `cgi-bin` 目录）、在文件系统找文件；后缀开头的 `/` 表示请求内容的起始目录；最小后缀 `/` 展开为配置的默认文件名（通常是 `index.html`）。

**HTTP 请求**：请求行 + 零个或多个请求头。
- 请求行：`<method> <uri> <version>`；method 为 `GET`/`POST`/`OPTIONS`/`HEAD`/`PUT`/`DELETE`/`TRACE`；uri 对代理是完整 URL、对服务器是 URL 后缀；version 如 `HTTP/1.1`；
- 请求头：`<header name>: <header data>`，给服务器附加信息（浏览器品牌、源服务器域名等）；
- **每个文本行以 `\r\n` 结尾；空行（`\r\n`）终止请求和响应头**。

**HTTP 响应**：响应行 + 零个或多个响应头 +（可选）内容，空行分隔头与内容。
- 响应行：`<version> <status code> <status msg>`；常见：`200 OK`（无错处理）、`301 Moved`（提供替代 URL）、`404 Not found`（服务器找不到文件）；
- 响应头：`Content-Type`（响应体 MIME 类型）、`Content-Length`（响应体长度）。

**完整 HTTP 事务示例**（`telnet www.cmu.edu 80`）：`GET / HTTP/1.1` + `Host: www.cmu.edu` + 空行 → 服务器回 `HTTP/1.1 301 Moved Permanently` 及 5 个响应头（`Location:` 指明页面已搬走）→ 空行 → chunked 内容体 → 服务器关连接。

**HTTP/1.0 vs HTTP/1.1 的主要区别**：
- HTTP/1.0：每个事务一条新连接；HTTP/1.1：支持**持久连接**（`Connection: Keep-Alive`，同一连接多个事务）；
- HTTP/1.1 **要求 Host 头**——使单个互联网主机可托管多个网站；
- HTTP/1.1 支持**分块编码**（`Transfer-Encoding: chunked`）；
- HTTP/1.1 增加缓存支持。

**数据传输机制**：标准方式用 `Content-Length` 指定总长度（要求程序缓冲整个消息）；chunked 方式把消息拆块、每块前缀十六进制字节数，最后 `0\r\n` 表示结束（如 `d75` = 3445 字节块 + 0 块）。

## 10. Tiny Web 服务器

**Tiny** 是教材中的**顺序 Web 服务器**（239 行带注释的 C 代码），能向真实浏览器提供静态和动态内容（文本、HTML、GIF/PNG/JPEG 图片）。不如真实服务器完整健壮——不规范的 HTTP 请求（如用 `\n` 而非 `\r\n` 结尾）就能弄坏它。

**Tiny 的操作流程**：接受客户端连接 → 读请求（经已连接 socket）→ 拆成 `<method> <uri> <version>` → 若 method 不是 GET 返回错误 → 若 URI 含 `cgi-bin` 则服务**动态内容**（fork 子进程执行程序；注：文件 `abcgi-bingo.html` 会被误判）→ 否则服务**静态内容**（把文件拷到输出）。

**服务静态内容**（`serve_static`）：

```c
void serve_static(int fd, char *filename, int filesize)
{
    int srcfd;
    char *srcp, filetype[MAXLINE], buf[MAXBUF];
    /* Send response headers to client */
    get_filetype(filename, filetype);
    sprintf(buf, "HTTP/1.0 200 OK\r\n");
    sprintf(buf, "%sServer: Tiny Web Server\r\n", buf);
    sprintf(buf, "%sConnection: close\r\n", buf);
    sprintf(buf, "%sContent-length: %d\r\n", buf, filesize);
    sprintf(buf, "%sContent-type: %s\r\n\r\n", buf, filetype);
    Rio_writen(fd, buf, strlen(buf));

    /* Send response body to client */
    srcfd = Open(filename, O_RDONLY, 0);
    srcp = Mmap(0, filesize, PROT_READ, MAP_PRIVATE, srcfd, 0);
    Close(srcfd);
    Rio_writen(fd, srcp, filesize);
    Munmap(srcp, filesize);
}
```

关键点：先用 `sprintf` 拼装响应头（`HTTP/1.0 200 OK`、`Server`、`Connection: close`、`Content-length`、`Content-type`），再用 `mmap` 把文件映射进内存、一次 `rio_writen` 写出——**把文件内容经已连接 socket 直接写给客户端**。

## 11. 动态内容与 CGI

**问题链**（Tiny 服务动态内容时）：
1. 客户端怎么把程序参数传给服务器？—— **参数附加在 URI 上**：`http://add.com/cgi-bin/adder?15213&18213`（参数表以 `?` 开始、`&` 分隔、空格用 `+` 或 `%20`）；
2. 服务器怎么把参数传给子进程？—— 放进**环境变量 `QUERY_STRING`**（`?` 之后的所有内容，如 `"15213&18213"`），CGI 程序用 `getenv` 读取：
```c
if ((buf = getenv("QUERY_STRING")) != NULL) {
    p = strchr(buf, '&');
    *p = '\0';
    strcpy(arg1, buf);
    strcpy(arg2, p + 1);
    n1 = atoi(arg1);
    n2 = atoi(arg2);
}
```
3. 服务器怎么把请求相关信息传给子进程？—— 同样经环境变量（真实服务器会设置全部 CGI 变量）；
4. 服务器怎么捕获子进程产生的内容？—— **子进程的输出在 stdout，服务器用 `dup2` 把 stdout 重定向到已连接 socket**：

```c
void serve_dynamic(int fd, char *filename, char *cgiargs)
{
    char buf[MAXLINE], *emptylist[] = { NULL };
    /* Return first part of HTTP response */
    sprintf(buf, "HTTP/1.0 200 OK\r\n");
    Rio_writen(fd, buf, strlen(buf));
    sprintf(buf, "Server: Tiny Web Server\r\n");
    Rio_writen(fd, buf, strlen(buf));
    if (Fork() == 0) { /* Child */
        setenv("QUERY_STRING", cgiargs, 1);
        Dup2(fd, STDOUT_FILENO);          /* Redirect stdout to client */
        Execve(filename, emptylist, environ); /* Run CGI program */
    }
    Wait(NULL); /* Parent waits for and reaps child */
}
```

**CGI (Common Gateway Interface)**：回答上述问题的规范。按 CGI 规范写的子进程叫 **CGI 程序**。它定义了客户端（浏览器）、服务器、子进程之间的信息传递标准；是动态内容的**原始标准**，如今大多被更快的技术取代（fastCGI、Apache 模块、Java servlets、Rails 控制器）——因为**临时创建进程昂贵且慢**。

**CGI 程序自己生成响应头**：注意 `adder.c` 里 `printf("Content-length: ...")`、`printf("Content-type: ...")` —— 因为**只有 CGI 子进程知道内容的类型和长度**，所以这些头由它产生。

完整事务示例：`GET /cgi-bin/adder?15213&18213 HTTP/1.0` → 服务器先回 `HTTP/1.0 200 OK` + `Server: Tiny Web Server`，随后 CGI 程序回 `Content-length: 117`、`Content-type: text/html` 与内容体 `Welcome to add.com: ... The answer is: 15213 + 18213 = 33426`。

## 12. 代理服务器

**代理 (proxy)** 是客户端与**源服务器 (origin server)** 之间的中介：
- 对客户端，代理**扮演服务器**；对源服务器，代理**扮演客户端**；
- 流程：① 客户端请求代理 → ② 代理请求源服务器 → ③ 服务器响应代理 → ④ 代理响应客户端。

**为什么要代理**：请求/响应经过时可以执行有用功能——**缓存 (caching)**、日志、匿名化、过滤。缓存例：客户端 A 请求 `foo.html` 时代理向源服务器取来并缓存；客户端 B 请求同一文件时直接命中缓存——**快速廉价的本地网络**替代**慢而贵的全球网络**。
