## 1. 分配器要解决的问题

程序里有些数据结构的大小**只有到运行时才知道**，于是需要一种机制在运行时向系统"要内存"——这就是**动态内存分配器 (dynamic memory allocator)**，它管理进程虚拟内存中称为**堆 (heap)** 的区域（位于 `.bss` 之上、共享库映射区之下，"break" 以上，可用 `sbrk` 系统调用伸缩）。

```c
void example(long n) {
    long *p;
    p = (long *)malloc(sizeof(long) * n);   // 运行时才知道要 n 个 long
    for (long i = 0; i < n; i++) {
        p[i] = i;
    }
    ...
    free(p);
}
```

分配器把堆维护为**一系列可变大小的块 (blocks)**，每块要么**已分配 (allocated)**、要么**空闲 (free)**。两类分配器：

- **显式分配器 (explicit allocator)**：应用负责分配**和释放**——C 的 `malloc`/`free`；
- **隐式分配器 (implicit allocator)**：应用只分配、不释放——Java 的 `new` + 垃圾回收。

## 2. malloc 包

```c
#include <stdlib.h>
void *malloc(size_t size)
```

- **成功**：返回至少 `size` 字节、**16 字节对齐**（x86-64）的内存块指针；`size == 0` 时返回 NULL；
- **失败**：返回 NULL (0) 并设置 `errno`。

```c
void free(void *p)
```

把 `p` 指向的块归还给可用内存池；`p` 必须是之前 `malloc`/`calloc`/`realloc` 的返回值。

其他函数：`calloc`（malloc + 初始化为零）、`realloc`（改变已分配块的大小）、`sbrk`（分配器内部用来增长/收缩堆）。

**malloc 为什么难**：谁决定 malloc/free 请求的顺序？分配块的生存期多长？malloc 何时必须返回？分配后能否搬动块？完美的 malloc 应该有哪些属性？——这些问题的答案互相牵扯，使 malloc 成为经典难题。

## 3. 约束与性能目标

**应用侧约束**：可发出**任意序列**的 malloc/free 请求；free 请求必须指向 malloc 过的块。

**分配器侧约束**（不能违反）：
- 无法控制已分配块的数目与大小；
- 必须**立即响应** malloc 请求（不能重排或缓冲请求）；
- 只能从**空闲内存**里分配（不能碰已分配块）；
- 必须满足**对齐要求**（x86-64 上 16 字节）；
- 只能操作和修改**空闲**内存；
- **不能搬动已分配块**——即不允许压实 (compaction)。为什么？因为应用持有指向块的指针，搬动后指针就失效了。

**两个互相冲突的目标**：

1. **吞吐量 (throughput)**：单位时间完成的请求数。例：10 秒内 5000 次 malloc + 5000 次 free = 1000 次操作/秒。
2. **峰值利用率 (peak utilization)**：最小化**开销 (overhead)**——给定请求序列，尽量让堆小。

讲义用 malloc lab 附带的基准 `syn-array-short`（20 步：`a`=allocate、`f`=free，先分配后释放，共 10 个块）演示：`Allocated` 是当前累计分配量，`Peak` 是历史最大值；生产级分配器还能在合适时机**收缩堆**。

## 4. 碎片化

内存利用率差源于**碎片化 (fragmentation)**，分两种：

**内部碎片 (internal fragmentation)**：某块的 **payload 小于块大小**。来源：维护堆数据结构的开销、对齐的填充 (padding)、显式策略决定（如用大块满足小请求）。只依赖**过去的请求模式**，所以容易测量。讲义基准中"完美分配器"因内部碎片也有 1.5% 开销（实际达不到，因为不能搬动块）。

**外部碎片 (external fragmentation)**：**总空闲内存足够，但没有单个空闲块够大**。依赖**未来的请求模式**，所以难以测量。例：

```
p1 = malloc(32)  p2 = malloc(40)  p3 = malloc(48)  free(p2)  p4 = malloc(64)?
```

`p2` 释放出的 40 字节夹在 p1、p3 之间，`p4` 要 64 字节——总空闲够（若 p1/p3 也释放），但单个块不够。讲义基准中 best-fit 策略下外部碎片带来的总开销是 8.3%。

> 直觉：内部碎片是"盒子里装不满"（浪费在块内部），外部碎片是"零钱凑不成整"（浪费在块之间）。

## 5. 实现问题概览

一个分配器必须回答五个问题：

1. **给一个指针，怎么知道要释放多少内存？** —— 在块前面存长度（header）；
2. **怎么跟踪空闲块？** —— 四种方法（见 §6、§12、§13）；
3. **分配的块比所在空闲块小，多余空间怎么办？** —— 分割 (split)；
4. **怎么选一个块来分配（可能有多个合适）？** —— 放置策略；
5. **释放后的块怎么复用？** —— 合并 (coalesce)。

**如何知道释放多少**：标准做法是把块的长度（字节数，**含 header**）存在块前一个字的 **header 字段**里——每个已分配块多花一个字。

**跟踪空闲块的四种方法**：
1. **隐式链表**：用长度字段链接**所有**块（含已分配的）；
2. **显式链表**：只在**空闲块**之间用指针链接；
3. **分离空闲链表**：按大小类分多条链表；
4. **按大小排序的块**：用平衡树（如红黑树）组织，指针存在空闲块内，长度作键。

## 6. 方法一：隐式空闲链表

最简单也最基础的跟踪方案：用长度字段把**所有块**（含已分配的）串成一条"隐式"链表。这一节讲它的块格式、查找策略、分割与释放——以及为什么朴素释放会出问题。

### 块格式

每块需要**大小**和**分配状态**两个信息——但用两个字存太浪费。**标准技巧**：块对齐后地址的低位比特恒为 0，干脆把其中一个 0 位用作已分配/空闲标志：

```
┌──────────────────────┐
│ Size (总块大小)  │ a │   ← 1 个字（header），a = 1 已分配 / 0 空闲
├──────────────────────┤
│ Payload（应用数据）   │
├──────────────────────┤
│ 可选 padding          │
└──────────────────────┘
```

读 Size 时必须**掩掉**最低位：`header & ~0xF`（讲义用 `~0xfL` 是因为对齐到 16 字节，最低 4 位都是 0，其中 1 位用作 a）。

### 数据结构与访问

```c
typedef uint64_t word_t;

typedef struct block {
    word_t header;
    unsigned char payload[0];   // 零长数组：payload 紧跟 header
} block_t;

// 由 block 指针取 payload
return (void *) (block->payload);

// 由 payload 指针（bp）取 block 指针：用 offsetof 精确回退
return (block_t *) ((unsigned char *) pp - offsetof(block_t, payload));

// 取分配位 / 取大小 / 初始化 header
return header & 0x1;
return header & ~0xfL;
block->header = size | alloc;
```

`offsetof(struct, member)` 返回成员在结构体内的偏移——这里恰好等于 header 的大小。

### 遍历与查找

相邻块在内存中紧挨着，已知当前块即可定位下一块：

```c
static block_t *find_next(block_t *block) {
    return (block_t *) ((unsigned char *) block + get_size(block));
}
```

**三种放置策略**：

| 策略 | 做法 | 特点 |
|---|---|---|
| **首次适配 (first fit)** | 从表头开始，选**第一个**够大的空闲块 | 最坏线性时间；实践中会在表头产生"碎片"（splinters） |
| **下次适配 (next fit)** | 像 first fit，但从**上次搜索结束处**开始 | 通常更快（不重扫无用块）；研究认为碎片更严重 |
| **最佳适配 (best fit)** | 搜索全部，选**剩余最小**的合适块 | 碎片最小、利用率最高；通常比 first fit 慢；仍是贪心，不保证最优 |

讲义基准（该测试集）的总开销对比：Perfect Fit 1.6% < Best Fit 8.3% < First Fit 11.9% < Next Fit 21.6%。

```c
static block_t *find_fit(size_t asize) {
    block_t *block;
    for (block = heap_start; block != heap_end;
         block = find_next(block)) {
        if (!(get_alloc(block)) && (asize <= get_size(block)))
            return block;
    }
    return NULL;   // 没有合适的块
}
```

### 分割（Splitting）

请求比空闲块小的时候，把空闲块劈成"已分配 + 剩余空闲"两块：

```c
// 注意：这段代码不完整（缺 footer 处理，见 §7）
static void split_block(block_t *block, size_t asize) {
    size_t block_size = get_size(block);
    if ((block_size - asize) >= min_block_size) {
        write_header(block, asize, true);
        block_t *block_next = find_next(block);
        write_header(block_next, block_size - asize, false);
    }
}
```

只有当剩余部分 ≥ 最小块大小时才值得分割。

### 朴素释放的问题

只清掉 allocated 位会导致**假碎片**：释放 `p` 后，`p` 与相邻空闲块本是连续空闲空间，但分配器"看不见"——`malloc(5*SIZ)` 明明有足够的**连续**空闲空间却找不到。**必须合并 (coalesce)**。

## 7. 合并与边界标记

**向前合并容易**：free(p) 后检查 `find_next(p)` 是否空闲，是则合并。

**向后合并难**：怎么知道**前一个**块从哪开始、是否空闲？答案——**边界标记 (boundary tags) [Knuth 73]**：把 size/allocated 字**复制到空闲块的底部**（footer），使链表可以**反向遍历**。代价是每块多花一个字（内部碎片），但这是**重要且通用的技术**。

```
┌──────────────────────┐
│ Size │ a │           │  ← header（在块开头）
├──────────────────────┤
│ Payload 和 padding    │
├──────────────────────┤
│ Size │ a │           │  ← boundary tag / footer（在块末尾）
└──────────────────────┘
```

footer 定位：当前块 footer 在 `payload + asize - dsize`；前一块 footer 就在 `&(block->header) - 1`（紧贴当前 header 前面一个字）。

```c
const size_t dsize = 2 * sizeof(word_t);   // header + footer
static word_t *header_to_footer(block_t *block) {
    size_t asize = get_size(block);
    return (word_t *) (block->payload + asize - dsize);
}
static word_t *find_prev_footer(block_t *block) {
    return &(block->header) - 1;
}
```

带 footer 的完整分割：

```c
static void split_block(block_t *block, size_t asize) {
    size_t block_size = get_size(block);
    if ((block_size - asize) >= min_block_size) {
        write_header(block, asize, true);
        write_footer(block, asize, true);
        block_t *block_next = find_next(block);
        write_header(block_next, block_size - asize, false);
        write_footer(block_next, block_size - asize, false);
    }
}
```

## 8. 常量时间合并的四种情况

释放块 `n`（大小 n），检查前块（大小 m1）与后块（大小 m2）的空闲状态，**O(1)** 合并：

| 情况 | 前块 | 后块 | 结果 |
|---|---|---|---|
| 1 | 已分配 | 已分配 | 只标记 n 空闲 |
| 2 | 已分配 | 空闲 | 与后块合并：header(m1) + 合并块 n+m2 |
| 3 | 空闲 | 已分配 | 与前块合并：合并块 n+m1（更新前块 header） |
| 4 | 空闲 | 空闲 | 三块合并：m1 + n + m2，更新前块 header 与后块 footer |

关键：footer 让我们**无需扫描**就能知道前块的分配状态和大小。

## 9. 堆结构与顶层代码

堆首尾各放一个**哑块 (dummy)**，防止 free 第一块/最后一块时意外合并：

- 第一个 header 之前的**哑 footer**（标记为已分配）——free 首块时它"假装"前块已分配；
- 最后一个 footer 之后的**哑 header**（已分配）——free 末块时它"假装"后块已分配。

```c
const size_t dsize = 2 * sizeof(word_t);

void *mm_malloc(size_t size) {
    size_t asize = round_up(size + dsize, dsize);  // 请求大小 + header/footer，向上取整对齐
    block_t *block = find_fit(asize);
    if (block == NULL)
        return NULL;
    size_t block_size = get_size(block);
    write_header(block, block_size, true);
    write_footer(block, block_size, true);
    split_block(block, asize);          // 有余量就分割
    return header_to_payload(block);
}

void mm_free(void *bp) {
    block_t *block = payload_to_header(bp);
    size_t size = get_size(block);
    write_header(block, size, false);
    write_footer(block, size, false);
    coalesce_block(block);
}
```

其中 `round_up(n, m) = m * ((n + m - 1) / m)`（向上取整到 m 的倍数，保证对齐）。

## 10. 优化：分配块不需要 footer

边界标记的内部碎片能否优化？**哪类块真正需要 footer？** 只有**释放时**才需要向后合并；而已分配块在释放前不参与合并——所以：

- **只有空闲块需要 footer**；
- 块大小是 16 的倍数时，header 有 **4 个空闲位**——用 2 位即可：
  - `a`：当前块是否已分配；
  - `b`（复用 header 的另一个对齐位）：**前一块**是否已分配。

于是**已分配块不再带 footer**（省一个字），空闲块仍带 footer（b 位在 free 时也已知前块状态，可从空闲块的 footer 读）。Header 编码：`(前块已分配)<<1 | (当前块已分配)`。四种合并情况依然可以 O(1) 判断。

> 注意：优化后前块是否空闲可以从**当前块 header 的 b 位**读；合并时若前块空闲，需要**前块的 footer** 拿到它的起始位置——而前块是空闲块，footer 一定存在。这就是"只给空闲块留 footer"能工作的原因。

## 11. 关键策略总结

- **放置策略 (placement)**：first-fit / next-fit / best-fit 等——**吞吐量与碎片程度之间的权衡**；有意思的观察：分离空闲链表（§13）**近似 best-fit**，却不用搜索整条链表；
- **分割策略 (splitting)**：什么时候分割空闲块？愿意容忍多少内部碎片？
- **合并策略 (coalescing)**：**立即合并**（每次 free 都合并）vs **延迟合并**（deferred，把合并拖到需要时，提高 free 性能）。

**隐式链表总结**：实现非常简单；分配**最坏线性时间**；释放**最坏常量时间**（含合并）；内存开销取决于放置策略。因为线性时间分配，**实际 malloc/free 不用它**（多用于专用场合），但**分割与边界标记合并是所有分配器的通用概念**。

## 12. 方法二：显式空闲链表

隐式链表扫描**所有**块（含已分配的）；显式链表只在**空闲块**间维护链表，把 next/prev 指针**存进空闲块的 payload 区**（反正空闲块没有数据）。

```
┌──────────────────────┐
│ Size │ a │           │  ← header
├──────────────────────┤
│ Next（指下一个空闲块） │
│ Prev（指上一个空闲块） │  ← 只占空闲块的 payload 区
├──────────────────────┤
│ （可选 padding）       │
├──────────────────────┤
│ Size │ a │           │  ← footer（仍需边界标记：合并要按内存序找相邻块）
└──────────────────────┘
```

**逻辑上**空闲块按链表序排列；**物理上**（内存序）可以是任意顺序——"next" 块可以在堆里任何位置，所以必须存显式指针，而不是靠地址步进。

**释放时的插入策略 (insertion policy)**：

| 策略 | 做法 | 优缺点 |
|---|---|---|
| **无序 LIFO** | 新释放块插到链表头 | 简单、常量时间；研究认为碎片比地址序更差 |
| **无序 FIFO** | 插到链表尾 | 同上 |
| **地址序 (address-ordered)** | 保持 `addr(prev) < addr(curr) < addr(next)` | 需要搜索；研究认为碎片最低 |

LIFO 释放有四种情况：相邻前/后块为空闲时，先从链表中 **splice out** 该块、合并内存块、再把合并结果插到链表头。

**实现技巧**：用**循环双向链表**，一个数据结构支持多种策略——first-fit 与 next-fit 只是让搜索指针 (free pointer) 固定还是随搜索移动；LIFO 与 FIFO 只是插入到 next 还是 prev 位置。

**显式链表总结**：分配时间是**空闲块数**的线性（而非所有块数）——内存几乎占满时快得多；分配/释放稍复杂（要 splice）；每个空闲块多花 **2 个字**存指针（内部碎片增加）。

## 13. 方法三：分离空闲链表

**分离空闲链表 (segregated free list, seglist)**：按大小类维护**多条**空闲链表，如 `16 | 32-48 | 64-∞ | ...`（每类一条）。分配时按大小落到对应类，只搜该类的链表；释放时合并后放回**合适**的类。

**相对非分离（同为 first-fit）的优点**：
- **更高的吞吐量**：2 的幂大小类下，搜索是 **log 时间**而非线性；
- **更好的内存利用率**：对分离链表做 first-fit **近似于对整个堆做 best-fit**；极端情况——每个块一个独立大小类 = 等价于 best-fit。

> 直觉：分离链表是"把零钱按面值分类存放"——找 5 元零钱只翻 5 元抽屉，不用翻整个钱包；而最合适面值的抽屉里的第一张往往就是最优选择。

参考资料：Knuth《TAOCP》卷 1 是动态存储分配的经典文献；Wilson et al. 1995 的综述 (CS:APP 学生站可下载) 是全面调研。

## 14. 内存危害与调试工具

学完分配器设计，还要知道**用错**它会出什么事：七种经典内存危害是 C 程序错误的集中来源，各有典型代码形态；最后给出一组定位它们的工具。

### 七种内存危害

**1. 解引用坏指针 (dereferencing bad pointers)**——经典的 scanf bug：

```c
int val;
scanf("%d", val);   // 应该传 &val；把 val 的值当地址写，运气好才 crash
```

**2. 读未初始化内存**——错误假设堆数据已清零：

```c
int *matvec(int **A, int *x) {
    int *y = malloc(N * sizeof(int));   // 未初始化！
    ...
    y[i] += A[i][j] * x[j];             // y[i] 读的是垃圾值
}
```
修法：用 `calloc`。

**3. 覆盖内存 (overwriting memory)**——五种子类：
- **分配了错误大小的对象**：`p = malloc(N*sizeof(int))` 却当 `int **` 用（应为 `N*sizeof(int *)`）；
- **差一错误 (off-by-one)**：`for (i=0; i<=N; i++)` 越界写；`p = malloc(strlen(s))` 少了 `+1` 放 `'\0'`；
- **不检查最大字符串长度**：`gets(s)` 是缓冲区溢出攻击的基础（见 [[第3章-程序的机器级表示#缓冲区溢出]]）；
- **误解指针算术**：`p += sizeof(int)` 实际前移 `sizeof(int)` 个 `int`——应为 `p++`；
- **解引用指针而非其指向的对象**：

```c
*size--;   // 实际是 size--（移动指针），而不是 (*size)--（减小值）
```
C 中后缀 `--` 优先级高于解引用 `*`（结合 K&R 的运算符优先级表）。

**4. 引用不存在的变量**——局部变量在函数返回后消失：

```c
int *foo() {
    int val;
    return &val;   // 悬垂指针！栈帧已销毁
}
```

**5. 多次释放同一块 (double free)**——nasty，且常可利用：

```c
x = malloc(N * sizeof(int));
free(x);
y = malloc(M * sizeof(int));
free(x);   // 第二次 free x，分配器数据结构已被破坏
```

**6. 引用已释放的块 (use-after-free)**——evil，且常可利用：

```c
free(x);
y = malloc(M * sizeof(int));
for (i = 0; i < M; i++)
    y[i] = x[i]++;   // x 已释放，可能已被 y 复用
```

**7. 未释放块 (内存泄漏 memory leak)**——缓慢的长期杀手：只释放链表头节点却丢掉其余节点；`free(head)` 前应先遍历释放全部 `next`。

### 调试工具

| 工具 | 适用 |
|---|---|
| **gdb** | 找坏指针解引用；难以发现其他内存 bug |
| **数据结构一致性检查器** | 静默运行、出错才打印——作为探针定位错误（如 malloc lab 的 `mm_check`） |
| **valgrind** | 二进制翻译器，重写可执行文件的 `.text`，运行时逐引用检查：坏指针、越界写、引用超出分配块 |
| **glibc 内置检查** | `setenv MALLOC_CHECK_ 3` 启用 malloc 自检 |
