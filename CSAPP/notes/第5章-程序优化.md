## 1. 编译器优化的目标与局限

### 优化目标

- **最小化指令数**：计算不重复做；不必要的计算完全不做；避免慢指令（乘法、除法）。
- **避免等待内存**：尽量把东西放在寄存器；用缓存友好的访问模式；**尽早且只加载一次**数据。
- **避免分支**：不做不必要的判断；让 CPU 更容易预测分支方向；**"展开"循环**摊薄分支成本。

### 优化的局限（Limits）

- **一般不能改进算法复杂度**——只能改善常数因子，但常数因子可能值 **10 倍以上**。
- **绝不能改变程序行为**——程序员可能不在乎"边界情况"行为，但编译器不知道；例外：语言规范可能声明某些改动可接受（如浮点结合律）。
- **通常一次只分析一个函数**——全程序分析（**LTO**）昂贵但正流行；例外：**内联**把多个函数合并成一个。
- **难以预知运行时输入**——**基于轮廓的优化 (profile-guided)** 可优化常见情形，但"最坏情况"性能可能同样重要——尤其是暴露给恶意输入（如网络服务器）的代码。

### 两类优化

| 类型 | 作用范围 | 例子 |
|---|---|---|
| **局部优化 (Local)** | 单个基本块内部 | 常量折叠、强度削减、死代码消除、（局部）CSE |
| **全局优化 (Global)** | 整个函数的控制流图 | 循环变换、代码移动、（全局）CSE |

> **历史**：Grace Hopper 发现第一个 bug（一只飞蛾）、1951 年发明第一个编译器（COBOL 前身）；John Backus 1957 年为 IBM 704 开发 FORTRAN；Fran Allen 1966 年引入**控制流图**概念、首位 ACM 图灵奖女性得主。

> **核心结论**：编译器优化追求"少指令、少等内存、少分支"，但受算法复杂度、行为不变性、单函数分析与运行时输入未知的限制；局部优化在基本块内、全局优化在整个函数上。

## 2. 优化示例

### 常量折叠（Constant Folding）

- **在编译器里做算术**：

```c
long mask = 0xFF << 8;   →   long mask = 0xFF00;
```

- 任何输入全为常量的表达式都可折叠；厉害的编译器甚至能折叠库调用：

```c
size_t namelen = strlen("Harry Bovik");   →   size_t namelen = 11;
```

### 死代码消除（Dead Code Elimination）

- **不发出永远不会执行的代码**：`if (0) { … }`、`if (1) { … }`。
- **不发出结果被覆盖的代码**：`x = 23; x = 42;`（只保留 `x = 42`）。
- 看似可笑，但：死代码可能**由其他优化产生**；对 `x` 的两次赋值可能相隔很远。

### 公共子表达式消除（Common Subexpression Elimination）

- **把重复计算提取出来，只算一次**：

```c
norm[i] = v[i].x*v[i].x + v[i].y*v[i].y;
   →
elt = &v[i];
x = elt->x;
y = elt->y;
norm[i] = x*x + y*y;
```

原表达式读内存 4 次，提取后地址只算一次、`x`/`y` 各加载一次、算术全在寄存器中。

### 代码移动（Code Motion）

- **把计算移出循环**——仅当**每次迭代结果相同**（循环不变量）才合法：

```c
for (j = 0; j < n; j++)  a[n*i+j] = b[j];
   →
int ni = n*i;
for (j = 0; j < n; j++)  a[ni+j] = b[j];
```

### 内联（Inlining）

- **把函数体复制到调用处**：省去调用开销，并**创造大量其他优化的机会**；但可能使代码**变大变慢**（指令缓存 i-cache）。

```c
/* 调用三个 pred() */
int func(int y) { return pred(y) + pred(0) + pred(y+1); }
int pred(int x) { if (x == 0) return 0; else return x - 1; }
```

内联后每个调用点可按 `x` 的实际值优化：`pred(0)` 恒真→折叠、`pred(y+1)` 的 `y+1==0` 判断被化简……最终得到：

```c
int func(int y) {
    int tmp = 0;
    if (y != 0) tmp = y - 1;
    if (y != -1) tmp += y;
    return tmp;
}
```

> C++ 模板函数（`std::string`、`std::map` 的实现几乎全在头文件里）正是为了让编译器能内联并化简。

> **核心结论**：五大基本优化——常量折叠（编译器做算术）、死代码消除（删无用代码）、CSE（重复计算只算一次）、代码移动（循环不变量提出去）、内联（复制函数体创造优化机会）。

## 3. 优化的障碍

### 内存别名（Memory Aliasing）

```c
void sum_rows1(double *a, double *b, long n) {
    for (i = 0; i < n; i++) {
        b[i] = 0;
        for (j = 0; j < n; j++)
            b[i] += a[i*n + j];
    }
}
```

- 编译器生成在**每次迭代都更新 `b[i]`** 的代码——为什么不能优化掉？
- 因为 **`b` 可能指向 `a` 内部**：每次写 `b[i]` 都可能改变后续要读的 `a` 元素。

**具体演示**——让 `b` 故意指向 `a` 内部：

```c
double A[9] = {0, 1, 2, 4, 8, 16, 32, 64, 128};
double B[3] = A + 3;        /* B 就是 A[3]~A[5] 的别名！ */
sum_rows1(A, B, 3);
```

- `B` 与 `A[3]~A[5]` 重叠，初始 `B = [4, 8, 16]`。逐外层循环看 `B`（= 对应位置的 `A`）如何变化：

| 阶段 | `B` 的值 | 发生了什么 |
|---|---|---|
| 初始 | `[4, 8, 16]` | `B[0]=A[3]=4`，`B[1]=A[4]=8`，`B[2]=A[5]=16` |
| i=0 | `[3, 8, 16]` | `b[0]=0` 覆盖 `A[3]`；再 `+= A[0..2]`：`0+1+2=3` |
| i=1 | `[3, 22, 16]` | 见下：`b[1]` 就是 `A[4]`，内层发生自引用 |
| i=2 | `[3, 22, 224]` | `b[2]=0` 覆盖 `A[5]`；再 `+= A[6..8]`：`32+64+128=224` |

- **i=1 那一步最微妙**：`b[1]` 与 `A[4]` 是同一个地址。内层 `b[1] += a[3+j]` 每次写回都改写了 `A[4]`，而 `j=1` 时读的 `a[4]` 正是刚被写回的 `b[1]` 自己：

```
j=0: b[1] += a[3]   →  0 + 3 = 3    （同时 A[4] 被写成 3）
j=1: b[1] += a[4]   →  3 + 3 = 6    （a[4] 就是 b[1] 自己！）
j=2: b[1] += a[5]   →  6 + 16 = 22
```

- 若不别名，本应是 `0 + 3 + 0 + 16 = 19`，实际得到 **22**——`b` 拿到的根本不是调用前 `a` 各行之和。编译器能看穿这种可能，因此**每轮迭代都从内存重读 `b[i]`、累加、写回**，而不是把 `b[i]` 提到寄存器里。

**如何避免别名代价**：

```c
void sum_rows2(double *a, double *b, long n) {
    for (i = 0; i < n; i++) {
        double val = 0;                 /* 用局部变量累计中间结果 */
        for (j = 0; j < n; j++)
            val += a[i*n + j];
        b[i] = val;                      /* 每外层循环只写一次 b[i] */
    }
}
```

- 用**局部变量**保存中间结果；
- 或用 **`restrict`** 关键字告诉编译器"这是指向该内存位置的唯一指针"。

### 函数调用阻碍代码移动（Function Calls Block Code Motion）

```c
void lower_quadratic(char *s) {                    /* O(n²)！ */
    for (i = 0; i < strlen(s); i++)                /* 每字符调一次 strlen */
        if (s[i] >= 'A' && s[i] <= 'Z')
            s[i] += 'a' - 'A';
}
```

- 编译器不知道 `strlen` 结果会不会变，**每轮循环都重新调用** → **"意外二次方 (accidentally quadratic)"**：把 32k 文本转小写要执行 7500 万条指令。
- GCC 知道 `strlen` 是**纯函数**（无副作用、返回值仅取决于参数及参数指向的数据），故只在字符串可能变化后调用——仍是二次方。
- **手动把 `strlen` 移到循环外**（`size_t n = strlen(s);` 一次），得到 **O(n) 的 `lower_linear`**：32kB 文本所用的周期，二次方版本只够处理 2kB。

> **核心结论**：**内存别名**（指针可能指向重叠区域）迫使编译器保守地每轮读写内存，用局部变量或 `restrict` 可消除；**函数调用**有副作用风险，编译器不能把调用移出循环，需程序员手动提循环不变量。

## 4. 机器相关优化：分支与流水线

### 现代 CPU：乱序执行与分支预测

- 现代 CPU 分两层：底部是**执行单元 (functional units)**——分支、算术（多个！）、加载、存储，多个算术单元可**同时**执行多条指令；顶部是**控制单元 (control unit)**——取指并派发指令，尽力让所有单元忙碌，必要时**乱序执行 (out-of-order)**：只要指令输入就绪且有空闲单元就执行。

![[Pasted image 20260819200251.png]]

- **难点在分支**：控制单元必须**远超前于执行单元**取指；若必须等 `cmp` 结果才决定继续往哪取，会浪费**数十周期**无事可做。
- 于是 CPU 做**分支预测 (branch prediction)**：猜测分支方向，在预测位置开始**推测执行 (speculative execution)**——这些指令**不真正修改寄存器/内存**。猜对了提交结果继续；猜错了**丢弃全部推测工作**、回滚寄存器状态、**重载流水线 (reload pipeline)**，从正确路径重新开始。
- 误预测代价：现代处理器上浪费**数十到数百周期**，是**重大性能限制器**（Spectre 硬件漏洞的根源正是"回滚重来"实现出错）。
- **循环示例**（数组长 100，预测 `jne` 跳转）：前 99 次预测正确；第 100 次 **Oops**——多执行 4 条指令、又取 4 条才发现猜错。

![[Pasted image 20260819201133.png]]

### 让分支可预测

**启发式 (heuristic) = 经验法则**：CPU 在还不知道 `cmp` 结果时就必须决定下一步往哪取指令（等不起，否则空等几十周期），只能"猜"，所以要挑平均最准的猜法：

- **向后分支 → 预测跳转**：循环的形状就是"末尾一条分支跳回更低的地址"。循环体跑 $N$ 次，这条分支 $N-1$ 次跳转、只在最后一次退出——猜"跳转"基本全对：

```asm
401029: mulsd (%rdx),%xmm0,%xmm0   # 循环体
40102d: add  $0x8,%rdx
401031: cmp  %rax,%rdx
401034: jne  401029                # 向后跳回循环头
```

- **向前分支 → 预测不跳转**：`if` 的形状是"不满足条件就跳过一块代码"。编译器布局代码时总是让**更可能执行的路径顺着 fall-through**，被跳过的多半是不常见代码——猜"不跳转"通常对。
- **更高级算法跟踪每条分支的行为**：静态规则不看历史；动态预测器给每条分支维护历史（如 **2-bit 饱和计数器**），**用过去预测未来**。"分支行为常相关"正指——一条分支（或相邻分支）过去的表现强烈预示未来的表现（循环分支跳 99 停 1、错误检查分支几乎从不跳），所以按历史猜非常准。
- **减少分支数量**：变换循环、**展开循环**（循环条件分支每 4 个元素才执行一次）、用**条件移动 (conditional moves)** 替代难预测的 if/else：

```c
/* 变换循环：把循环内不变的条件判断提出去，循环内不再有分支 */
if (flag)
    for (i = 0; i < n; i++) do_A(i);
else
    for (i = 0; i < n; i++) do_B(i);

/* 条件移动：if/else 选值 → 编译器生成无分支的 cmov */
if (x < 0) x = -x;          /* → cmovl %edx, %eax（无跳转） */
```

- **条件移动 (cmov)** 的小坑：cmov 只能**选值**、不能跳过内存写——被分支守卫的写会被改写成**无条件写回**（如"只在大写时写回"变成每个字符都被写回）。**写穿透缓存**下会白白增加内存流量；写回缓存则基本无碍——所以"并不总是好主意"。
- **让分支可预测**：给预测器制造规律——**对数据排序**（经典 Stack Overflow 案例）把"数据随机的抛硬币分支"变成"连串不跳→连串跳"的规律分支；**避免间接分支**（函数指针、虚方法），因为其目标在寄存器里、预测器连"跳去哪"都难猜：

```c
/* 数据相关分支：数据随机 → 约一半误预测；先排序 → 几乎全对 */
for (i = 0; i < n; i++)
    if (a[i] > 128) s += a[i];

/* 间接分支（函数指针）：目标在寄存器，难预测；直接调用则目标固定 */
int apply(int (*fp)(int), int x) { return fp(x); }
```

### 循环展开与调度

**循环展开 (loop unrolling)**：把循环体复制多份，**摊薄循环条件的成本**（条件与分支执行次数减到 1/4），并创造 CSE、代码移动、调度机会，为**向量化**做准备：

```c
for (i = 0; i < nelts; i++)  A[i] = B[i]*k + C[i];

for (i = 0; i < nelts - 4; i += 4) {
    A[i]   = B[i]  *k + C[i];
    A[i+1] = B[i+1]*k + C[i+1];
    A[i+2] = B[i+2]*k + C[i+2];
    A[i+3] = B[i+3]*k + C[i+3];
}
```

- 风险：代码变大（同内联）、寄存器不够用。
- **何时错误？** 当元素数不是 4 的倍数（需额外处理余数）。

**调度 (scheduling)**：**重排指令**让 CPU 更容易保持所有功能单元忙碌、并**藏住访存延迟**——例如把展开循环的**所有加载移到顶部**，让它们同时发出，数据返回后任意顺序做算术。这正解释了为什么需要**大量寄存器**（要先装下所有提前加载的中间值）：

```c
/* 不调度：每行 加载→乘→加→存 顺序执行 */
for (i = 0; i < nelts - 4; i += 4) {
    A[i]   = B[i]  *k + C[i];
    A[i+1] = B[i+1]*k + C[i+1];
    A[i+2] = B[i+2]*k + C[i+2];
    A[i+3] = B[i+3]*k + C[i+3];
}

/* 调度后：8 个加载提前一起发出，等内存时算术单元已在算 */
for (i = 0; i < nelts - 4; i += 4) {
    B0 = B[i]; B1 = B[i+1]; B2 = B[i+2]; B3 = B[i+3];
    C0 = C[i]; C1 = C[i+1]; C2 = C[i+2]; C3 = C[i+3];
    A[i]   = B0*k + C0;
    A[i+1] = B1*k + C1;
    A[i+2] = B2*k + C2;
    A[i+3] = B3*k + C3;
}
```

- **何时错误？** 当 `A` 与 `B` 或 `C` 重叠（别名），把加载提前改变了读写顺序——写 `A` 改变了正在读的 `B`/`C`。

> **核心结论**：现代 CPU 靠推测执行 + 乱序执行保持单元忙碌；分支误预测代价高昂（数十周期、Spectre 根源）。程序优化方向：减少分支（展开、条件移动）、让分支可预测（排序、避免间接分支）、展开循环并调度以利用指令级并行。

## 5. 基准示例：向量求和 combine

### 目标、数据结构与指标

- **目标**：把向量的所有元素累加（`OP`/`IDENT` 取 `+ / 0` 或 `* / 1`，`data_t` 取 `int`/`long`/`float`/`double`），度量不同写法的性能差距。
- **数据结构**：`vec = { len, data }`；`get_vec_element(v, i, &val)` 带**边界检查**——"正确但低效"的访问方式。

```c
typedef struct {
    size_t len;
    data_t *data;
} vec;

/* 安全访问：越界检查 + 输出参数 */
int get_vec_element(vec *v, size_t idx, data_t *val) {
    if (idx >= v->len)      /* 越界检查 */
        return 0;
    *val = v->data[idx];    /* 把第 idx 个元素写入 *val */
    return 1;
}
```

`get_vec_element(v, i, &val)` 里的 `&val` 是**输出参数**——C 传值，函数用 `*val` 把元素写回调用者的 `val`；返回值 1/0 表示成功/越界。它是"正确但低效"的取法（每次都做边界检查）；combine4 改用 `get_vec_start(v)` 直取 `data`、`d[i]` 免去检查。

- **指标 CPE（每元素周期数）**：$Cycles = CPE \times n + Overhead$，**CPE 是直线的斜率**——它比总时间更能说明"每个元素到底花几个周期"，便于对比不同实现。

### 版本 0：combine1——最朴素的写法

```c
void combine1(vec_ptr v, data_t *dest) {
    long int i;
    *dest = IDENT;
    for (i = 0; i < vec_length(v); i++) {
        data_t val;
        get_vec_element(v, i, &val);   /* 每次调用都有边界检查 */
        *dest = *dest OP val;
    }
}
```

三个低效点：① 每轮都重新调 `vec_length(v)`；② 每次 `get_vec_element` 都做边界检查；③ `*dest` 每轮从内存读、算、写回。未优化 **CPE ≈ 20**（整型加 22.68）。

### 版本 1：什么都不改，只换编译选项

编译器优化是**最容易的收益**：一行代码没改，`-O1` 把 CPE 降到约 10、`-O3` 再降到 **4.5–7.8**（具体见末尾对照表）。

### 版本 2：combine4——手写基础优化

```c
void combine4(vec_ptr v, data_t *dest) {
    long length = vec_length(v);   /* ① 把 vec_length 移出循环 */
    data_t *d = get_vec_start(v);  /* ② 免每轮边界检查 */
    data_t t = IDENT;              /* ③ 在临时变量中累加 */
    for (i = 0; i < length; i++)
        t = t OP d[i];
    *dest = t;
}
```

逐个对应版本 0 的三个低效点：把 `vec_length` 提出去、改用无检查的 `get_vec_start` 直取数组、在寄存器临时变量 `t` 里累加（不再每轮读改写 `dest`）。**CPE ≈ 1.3–5**（整型加 1.27）。

### 版本 3：unroll2a——循环展开

```c
void unroll2a_combine(vec_ptr v, data_t *dest) {
    long limit = length-1;
    data_t x0 = IDENT, x1 = IDENT;
    for (i = 0; i < limit; i += 2) {   /* 一次合并 2 个元素 */
        x0 = x0 OP d[i];
        x1 = x1 OP d[i+1];
    }
    for (; i < length; i++)            /* 处理剩余元素 */
        x0 = x0 OP d[i];
    *dest = x0 OP x1;
}
```

两条**独立的累加链** `x0`、`x1` 让多功能单元并行；展开后每轮循环只有 5 条指令（2 个 `addq` + 指针前进 + 比较 + 跳转），**每周期执行多条指令**。**CPE ≈ 0.8–2.5**。

### 获取高性能的总结

1. **好的编译器与编译选项**；
2. **不要做任何次优的事**：警惕隐藏的算法低效；写编译器友好代码——警惕优化阻断物（**过程调用与内存引用**）；仔细审视最内层循环（大部分工作所在）。
3. **为机器调优**：利用**指令级并行**；避免**不可预测分支**；让代码**缓存友好**。

> **核心结论**：从 combine1（约 20 CPE）到编译选项（3–5）、手写基础优化 combine4（1.3–5）、循环展开 unroll2a（0.8–2.5）——按"先编译器、再手写、再展开"的步骤逐级获得数量级提升。

## 总结

| 概念 | 要点 |
|---|---|
| **优化目标** | 少指令、少等内存、少分支 |
| **优化局限** | 不改算法复杂度、不改行为、单函数分析、运行时输入未知 |
| **基本优化** | 常量折叠、死代码消除、CSE、代码移动、内联 |
| **内存别名** | 指针重叠迫使保守读写；用局部变量或 `restrict` 消除 |
| **分支预测** | 推测执行 + 误预测回滚（数十周期）；排序数据、避免间接分支 |
| **循环展开与调度** | 摊薄循环成本、利用指令级并行；注意代码大小与别名 |
| **CPE** | 基准 combine：20 → 3–5（编译器）→ 1.3–5（基础优化）→ 0.8–2.5（展开） |
