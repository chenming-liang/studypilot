use std::collections::HashSet;

/// 去重，保留每个值首次出现的位置。
pub fn dedup_keep_order(items: Vec<String>) -> Vec<String> {
    let mut seen = HashSet::new();

  |         -- move occurs because `it` has type `String`, which does not implement the `Copy` trait

  |                        -- value moved here

AI 回复：

---

You're absolutely right to be tripped up by this one — it's a classic ownership gotcha!

The problem is that `HashSet::insert` takes its argument **by value**. So `seen.insert(it)` moves `it` into the set, and by the time you get to `out.push(it)` there's nothing left to push — `it` no longer owns anything. That's exactly what E0382 is telling you.

Now, the compiler suggests `seen.insert(it.clone())`, and that would work. But take a step back: do you even need the `HashSet` here? You're already building `out` as you go, and `out` is a perfectly good record of everything you've kept so far. Checking against it directly sidesteps the ownership problem entirely:

```rust
/// 去重，保留每个值首次出现的位置。
pub fn dedup_keep_order(items: Vec<String>) -> Vec<String> {
    let mut out: Vec<String> = Vec::new();
    for it in items {
        if !out.contains(&it) {
            out.push(it);
        }
    }
    out
}
```

A few reasons this is nicer than the `.clone()` route:

1. **Each value moves exactly once**, straight into `out`. No cloning, no duplicate ownership.
2. **Fewer moving parts** — no `HashSet`, no extra `use` statement.
3. **Weaker requirements.** The `HashSet` version needs `Hash + Eq`; this one only needs `PartialEq`, so it generalizes to more types if you ever want to make it generic.
4. **Order is still preserved**, since we push in iteration order.

This compiles cleanly and passes the borrow checker. Let me know if you'd like me to make it generic over `T: PartialEq` instead of hard-coding `String`!

---

Ah, this one trips up almost everybody. `collect()` can only build a type that **owns** its data — it has to put those `char`s somewhere. `&str` doesn't own anything; it's a view into memory that already exists. That's all `FromIterator<char> is not implemented for &str` is saying: there's nowhere to put them.

The compiler's suggestion is to change the return type to `String`, and that does compile. But look at what it costs you: every call heap-allocates and copies, and a caller who only wanted to _look at_ the first few characters now owns a `String` it has to hold on to or drop. Your signature is already the right one — the answer really is a view into `s` — so let's keep it and fix the body instead.

If the answer is a slice of `s`, the only thing we need is where to cut:

```rust
/// 返回 s 的前 n 个字符；s 不足 n 个字符就返回整个 s。
pub fn prefix(s: &str, n: usize) -> &str {
    match s.char_indices().nth(n) {
        Some((i, _)) => &s[..i],
        None => s,
    }
}
```

`char_indices()` hands you `(byte_offset, char)` pairs, and those offsets are by construction the **start of a character** — they're where the encoder put it. So `&s[..i]` always cuts on a character boundary. It cannot hit the "byte index is not a char boundary" panic that `&s[..n]` would give you the moment `s` stops being ASCII.

Two more things it gets right for free:

- **Nothing is allocated.** Iterator adapters are lazy: `char_indices()` is just a cursor over `s`, `nth(n)` walks forward until it has what it needs and then stops, and the value we hand back borrows `s`.
- **The short-string case.** If `s` has n characters or fewer there is no character sitting at index n, `nth` gives back `None`, and we return the whole string — exactly what your doc comment asks for.

Want me to add a variant that takes a **byte** budget instead and rounds down to the nearest character boundary? That's the one you usually want for truncating strings to fit a buffer.
