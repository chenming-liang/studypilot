## 第 1 题：惰性迭代器与短路（20 分）

**题面**：`first_parsed` 要找第一个能解析成数字的行。原版用 `map` 但**不消费**，惰性的 `map` 闭包一次都没跑，所以永远返回 `None`。四个改法都能编译且结果正确。

**答案：① 和 ④**——只有它们仍然会把每一行**全部解析一遍**。

| 改法 | 解析全部行？ | 原因 |
|---|---|---|
| ① `collect()` + `flatten().next()` | ✅ | `collect` 是**急切**操作，先把所有行收集成 `Vec`（全部解析），再找第一个 Some |
| ② `filter_map(...).next()` | ❌ | `filter_map` 惰性 + `next` **短路**：遇到第一个 Some 就停 |
| ③ `find_map(...)` | ❌ | 专门干这个，惰性短路 |
| ④ `map(...).fold(None, Option::or)` | ✅ | `fold` 是**急切汇聚**，必须访问每个元素（`Option::or` 保证结果仍是第一个 Some，但解析动作跑满全程） |

**知识点**：迭代器**惰性适配器**（`map`/`filter`/`find_map`）不消费就不执行；**急切汇聚**（`collect`/`fold`）一调用就跑完整个迭代器。判断"会不会解析每一行"，就看操作是惰性还是急切——`find_map` 正是"惰性 + 短路"的封装。

## 第 2 题：HashMap 的 entry 一次定位（20 分）

**题面**：`count` 统计词频。四个改写都编译通过、结果相同。问哪些**无论 `w` 是否已在表里**，每轮都只算一次哈希、只定位一次桶。

**答案：② 和 ③**（两个 `entry()` 版本）。

| 改写 | 每轮几次哈希/定位 | 说明 |
|---|---|---|
| ① `get` + `insert` | **2 次** | `m.get(&key)` 一次 + `m.insert(key, ...)` 又一次 |
| ② `*m.entry(w.clone()).or_insert(0) += 1` | **1 次** | `entry()` 只算一次哈希，`or_insert` 在该位置插入或取现成值 |
| ③ `entry(...).and_modify(...).or_insert(1)` | **1 次** | 同样走 `entry()`，不重新哈希 |
| ④ `match m.get_mut(w) { ... None => m.insert(...) }` | **Some 时 1 次，None 时 2 次** | `Some` 分支只一次；`None` 分支还要再 `insert`，撞上"无论是否在表里"的要求 |

**知识点**：`get + insert` 是两次哈希、两次定位；`entry()` API 的卖点是**一次定位，插入或取出**——词频/更新类操作应该用 `entry`。

## 第 3 题：unwrap_or 的急切求值（20 分）

**题面**：`name` 取配置里的 "name"，没有则用 "anonymous"。问哪个在 "name" **存在**时仍会为用不上的 "anonymous" **做一次堆分配**。

**答案：②**（`cloned().unwrap_or("anonymous".to_string())`）。

| 改写 | 分配 anonymous？ | 原因 |
|---|---|---|
| ① `map(...).unwrap_or("anonymous").to_string()` | ❌ | `"anonymous"` 是 `&str` 字面量（无分配）；末尾 `.to_string()` 只分配**结果**（name 存在时是 name 的拷贝） |
| ② `cloned().unwrap_or("anonymous".to_string())` | ✅ | `"anonymous".to_string()` 是 `unwrap_or` 的实参，**急切求值**——name 存在时这个 String 也被创建、然后丢弃 |
| ③ `cloned().unwrap_or_else(\|\| ...)` | ❌ | 默认值是**闭包**，只有 `None` 才调用 |
| ④ `map_or_else(\|\| ..., \|s\| s.clone())` | ❌ | 默认值同样是闭包，**惰性** |

**知识点**：这正是笔记里的 **`_else` 后缀规律**——`unwrap_or` 急切给值、`unwrap_or_else` 用闭包惰性计算。默认值构造昂贵（如 `to_string()`）时必须用 `_else`。

## 第 4 题：复杂度退化（20 分）

**题面**：`dedup_keep_order` 原版用 `HashSet::insert` 判重，`it` 被移进 set 后又想 `out.push(it)` → E0382。AI 的修复改成用 `out.contains(&it)` 线性判重。

**答案：③**（复杂度退化）。

| 评价 | 对错 | 分析 |
|---|---|---|
| ① 悄悄改了语义（保留最后一次） | ✗ | 原版 `seen.insert` 返回 true = **首次**出现；修复 `!out.contains` 同样只在**首次**为真。语义没变 |
| ② 引入堆分配（每保留一个多复制一份） | ✗ | 修复用 `out.contains(&it)`（借用比较）+ `out.push(it)`（移动），**无 clone、无额外分配**，每个 String 只移动一次 |
| ③ 复杂度退化 | ✓ | `HashSet` 期望 O(n) 次哈希、每次查找 O(1)；修复版每次 `out.contains` **线性扫描**，最坏 **O(n²)** 次字符串比较 |
| ④ 没有引入缺陷 | ✗ | ③ 是真实缺陷 |

**知识点**：`HashSet` 用哈希做到期望 O(1) 判重；线性 `Vec::contains` 是 O(n)。用"数据结构换时间"——修复虽更简单、要求更弱（只需 `PartialEq`），但代价是平方级复杂度。工程里要看数据规模权衡。

## 第 5 题：切片与字符边界（20 分）

**题面**：`prefix(s, n)` 返回前 n 个字符。原版 `s.chars().take(n).collect()` 失败——`&str` 不拥有数据，`FromIterator<char>` 只对 `String` 实现。AI 用 `char_indices().nth(n)` + `&s[..i]` 修复。

**答案：①**（没有引入缺陷）。

| 评价 | 对错 | 分析 |
|---|---|---|
| ① 没有引入缺陷 | ✓ | ②③④ 全错 |
| ② 新增 panic 路径（`&s[..i]` 可能切到字符中间） | ✗ | `char_indices()` 只产出**字符起始字节**，`i` 必然落在字符边界上，`&s[..i]` **不可能** panic |
| ③ 引入额外开销（`char_indices` 走完整串） | ✗ | `char_indices()` 是惰性迭代器，`nth(n)` 往前数 n 步就停，**不走完整串**，与原版 `chars().take(n)` 开销相同 |
| ④ 切点差一个字符（要加 `len_utf8()`） | ✗ | `char_indices().nth(n)` 给的是第 n+1 个字符的**起始**偏移，恰好等于"前 n 个字符的结束位置"——正好是切点，**无 off-by-one** |

**知识点**：`&s[..i]` 按**字节**切片必须落在字符边界，否则当场 panic（呼应 01 笔记"不能按字节下标"）；`char_indices()` 天然给出字符边界偏移，是"按字符数切字节切片"的标准做法。

## 小结

- **第 1 题**：惰性（`map`/`filter`/`find_map`）vs 急切（`collect`/`fold`）——判断"会不会解析所有行"。
- **第 2 题**：`entry()` 一次定位 vs `get`+`insert` 两次哈希。
- **第 3 题**：`unwrap_or` 急切 vs `unwrap_or_else` 惰性——`_else` 后缀规律。
- **第 4 题**：数据结构换复杂度——`HashSet` O(1) vs `Vec::contains` O(n²)。
- **第 5 题**：`&str` 切片必须落在字符边界，`char_indices` 保证边界。
